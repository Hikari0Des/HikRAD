## What shipped (FR-150–152)

- **Migrations 0614–0615** — the phase brief budgeted 0613–0614; the repo's
  real max at kickoff was already `0613` (v4-7's `nas_hotspot_pages`), so the
  master plan's "next free number, budgets are not reservations" rule moved
  the range up by one, the same renumbering v4-6/v4-7 themselves needed.
  `0614` is `coa_outbox` (subscriber/NAS/session identity, `action` — the
  ORIGINAL requested op, frozen — vs `current_op` — what's actually being
  attempted now, which flips on fallback —, the intended `attributes` set,
  `state` machine, attempt/fallback bookkeeping, `next_attempt_at` for
  dispatcher pacing). `0615` is `coa_attempts` (one row per dispatch attempt,
  `wire_attributes` jsonb) plus the two new hot-reloadable settings
  (`radius.coa_retry_max` default 3, `radius.coa_timeout_seconds` default 5)
  FR-151 asks for — sourced through the *existing* `platform.Settings`
  service, no new config mechanism.

- **`coa_dispatcher.go` is the package's only sender.** `internal/radius/coa.go`'s
  `send()` (the real UDP round trip — per-NAS secret/port, the
  version-aware `SupportsInPlace` short-circuit, the `coaMaxInflight`
  storm-safety cap, `exchangeWithRetry`'s one safety retry) is unchanged in
  its mechanics but is now called from exactly one place in the whole
  backend — confirmed by `grep -rn "\.send(ctx" internal/radius/*.go` outside
  `_test.go` returning a single hit, `coa_dispatcher.go:119`. The package-level
  `Disconnect`/`ApplyRate`/`MovePool` functions v1–v3 exposed are **deleted**;
  `coa_enqueue.go`'s `Enqueue`/`EnqueueDisconnect`/`EnqueueApplyRate`/
  `EnqueueMovePool`/`EnqueueUpdate` are the only way anything in this codebase
  can now cause a CoA to be sent, and every previous direct caller was
  refactored onto them: the enforcement worker (`enforce.go`), the continuous
  limits worker (`limitsworker.go`), the TOD sweep (`tod.go`), billing's
  renewal restore (`renew.go`'s `restoreCoA` — the hero flow) and refund
  rollback (`refund.go`'s `enforceExpiredCoA`), and the panel's manual
  disconnect (`live/coa_action.go`). None of these previously called through
  a shared seam that could be swapped once — each was its own call site, so
  this was five separate refactors, not one.

- **A real design collapse, not just a plumbing change.** The old code sent
  `move_pool` and `apply_rate` as two sequential CoA-Request packets with a
  hand-rolled retry/fallback state machine (`coaStep`/`runPlan`/`runStep` in
  `enforce.go`, duplicated in `limitsworker.go` as `planStepsForOutcome`).
  v4-8 deletes all of that: a crossing that needs both a pool move and a rate
  clamp (e.g. FR-9's expired-pool behavior) now enqueues **one** row carrying
  **both** attributes in a single combined `vendor.Attr` list — the
  dispatcher's hybrid fallback then treats the pair atomically (gate item 1's
  "nothing dispatches inline" forced this: two separate dispatch calls can no
  longer exist in the same code path once dispatch itself moved out of the
  caller's hands). `enforce.go`'s `planSteps` and `limitsworker.go`'s (renamed)
  `planForOutcome` now return `(CoAAction, []vendor.Attr, label)` instead of a
  step slice — smaller, and structurally unable to reintroduce the two-
  sequential-calls shape.

- **The hybrid fallback state machine (FR-151).** Faithful to the frozen §4
  contract's literal five states: a dispatch attempt failing (NAK/timeout/
  unsupported-in-place/error) parks the row in `nack` — a real, counted state,
  not a transient one — until a separate sweep pass (`nackSweep`/
  `decideNack`, pure and unit-tested) decides: retry while `attempt_count <
  coa_retry_max` (`→ pending`); once exhausted, an `update` row that hasn't
  fallen back yet switches `current_op` to `disconnect` with a fresh attempt
  budget and `fallback_used`/`fallback_at`/`fallback_reason` recorded on the
  SAME row (`→ pending`, picked up as `sent` on the next claim — never a
  second row); anything else (already a disconnect, or already fallen back
  once) is terminal (`→ failed`). One dispatch attempt per due row per tick
  (3 s) — never a tight synchronous retry loop — so the retry budget is
  genuinely spread across ticks and observable between them, per the phase
  brief's "Dispatcher runs on the worker tick" instruction.

- **The reaper interaction (gate item 8).** Before every dispatch attempt,
  `dispatchOne` checks the target session against C's live-state hash
  (`sessionStillLive`, the identical `livestate.HashKey`/`Field` lookup
  `live/coa_action.go` already used). Absent → `resolveReaped` marks the row
  `done` with `last_outcome = "skipped_reaped"`, no packet ever sent — never
  `failed`. Applied uniformly to both `update` and `disconnect` rows (a
  pool/rate change for a session that no longer exists is equally moot), a
  deliberate widening of the gate item's literal "disconnect" wording since
  the reasoning applies identically to either op.

- **Wire-level inspect evidence (FR-150 §3.1/§4, gate item 6).**
  `coa_wire.go`'s `dumpWireAttributes` reads the constructed
  `layeh.com/radius` packet's `Attributes` directly — generic byte-level
  decode (type, hex, best-effort printable text, and a Vendor-Specific
  (type 26) sub-decode into vendor-id/vendor-type/vendor-value) with **no**
  hardcoded vendor attribute name anywhere in this file, so it does not
  violate FR-17 vendor isolation (confirmed: `grep -rn "Mikrotik-"` across
  every v4-8 file returns nothing). Captured once, immediately after the
  packet is fully built and before the UDP exchange — deterministic
  regardless of outcome — and stored into `coa_attempts.wire_attributes`,
  never regenerated when the inspect view reads it back.

- **CoA Outbox screen (FR-152).** Backend: `GET /coa-outbox` (keyset-paginated,
  state/action filters, username/NAS/reason search — the same
  `(created_at, id)` cursor pattern `billing/tickets_api.go` established),
  `GET /coa-outbox/counters` (six counters + a `failed_24h` field for v4-12's
  dashboard pipeline-health panel), `GET /coa-outbox/{id}` (row + every
  attempt's wire bytes), `POST .../retry` (nack/failed only, resets to
  `pending` with the original action/attempt budget/fallback state cleared),
  `POST .../cancel` (pending only — a sent/resolved row 409s). New permission
  pair `coa_outbox.view`/`coa_outbox.manage` (`roles.go`'s catalog — admin
  gets it automatically via the wildcard, operator/agent do not by default,
  matching how `nas.reboot`/`nas.update` were added in v4-6/v4-7). Frontend:
  `CoaOutboxPage.tsx` (counters via `StatCard`, `FilterBar` for state/action +
  search, 8s poll-based auto-refresh, an inspect modal showing intended
  attributes and per-attempt wire bytes behind a disclosure toggle), a
  sidebar nav entry + pending-count badge (`usePendingCoACount`, the same
  30s-poll pattern `usePendingTicketCount` already established), full
  trilingual coverage (en/ar/ku, `i18n:check` clean).

## Deliberate scope decisions

- **`coa_port` stays exactly where it already was** (`nas.coa_port`, per-NAS)
  rather than becoming a new global setting — the phase brief's "existing
  hot-reloadable settings" instruction is read as "the existing settings
  *mechanism*, not a new config path," and a CoA port is a per-router fact
  the existing per-NAS field already models correctly. Only
  `coa_retry_max`/`coa_timeout_seconds` are new settings keys (seeded by
  migration 0615), replacing what were previously hardcoded Go constants.
- **`nack` is a real, separately-persisted state**, not collapsed into an
  immediate same-call decision — a dispatch attempt writes `nack` first, and
  a distinct sweep pass decides retry-vs-fallback-vs-fail. This costs one
  extra write per failed attempt but makes the six FR-152 counters (which
  explicitly list `nack` as its own bucket) literally true at any point in
  time, and makes the fallback transition genuinely observable between ticks
  rather than instantaneous.
- **The `EnforcementFailuresKey` Redis counter** (C's health page,
  `internal/monitorsvc/health_api.go`, unmodified) is now incremented by
  `coa_dispatcher.go` on a row's terminal `failed` resolution — the one place
  a CoA's real, final outcome is known post-v4-8 — instead of by the
  enforcement worker's old synchronous outcome. This makes the metric MORE
  accurate (every failure source: worker, renewal, panel disconnect — not
  just the enforcement worker's own) without any change to the health page
  itself.
- **A retry's own "retries" get a fresh budget after fallback** — when an
  `update` row falls back to `disconnect`, `attempt_count` resets to 0 so the
  disconnect leg gets its own full `coa_retry_max` attempts before terminal
  failure, rather than inheriting the update leg's exhausted count. Read
  literally, §4's `nack → sent` transition already implies a fresh attempt
  cycle begins; this is the natural way to make that concrete.
