## What shipped (FR-173–175)

### FR-173 — Reports: trend lines, daily traffic, top-10s, traffic by entity

`backend/internal/reports/trends.go` (trend lines, daily traffic, four top-10 lists) and
`traffic_entity.go` (paginated/searchable Users and Cards tabs). New endpoints:
`GET /api/v1/reports/trends`, `/daily-traffic`, `/top10`, `/traffic-by-entity` — all
`reports.view`-gated, matching the five pre-existing report endpoints' own posture
exactly (no new permission granularity invented for this phase).

**Migration 0633** (`usage_card_daily`) closes a real gap found while scoping this work:
0132 (v4 phase 2) built `usage_daily`, a continuous aggregate rolling up
`usage_points` by day/subscriber/NAS/service — but 0604 (v4-5, cards) added `card_id`
to `usage_points`/`sessions` and never extended the rollup, so a card-scoped query had
no rollup to read and would have had to scan the raw hypertable, exactly what FR-47
already forbids at panel-load budgets. 0633 adds the card-daily sibling aggregate;
**0634** adds its refresh/retention policy, mirroring 0132/0133's own split (a
continuous aggregate's creation can't share a transaction with anything else,
autocommit-only). Both migrations were applied directly against a live TimescaleDB
instance and verified with real-time aggregation (a freshly inserted `usage_points` row
with a `card_id` appeared in `usage_card_daily` immediately, no manual refresh) before
any Go code was written against them.

**Users and Cards never share a query** (gate item 2): Users reads `usage_daily`
joined to `subscribers`; Cards reads `usage_card_daily` joined through `cards` to
`card_groups` (a card has no name of its own — codes are hashed-only — so the Cards
tab's "entity" is the card group, matching where the phase brief's "rows linking to…
card group" phrasing points). Proven directly, not inferred: `TestTrafficByEntity_UsersAndCardsNeverMix`
seeds a subscriber and a card in the same window with different byte counts and asserts
neither tab's response contains the other's id, with the correct bytes on the row that
does appear.

**A real, pre-existing UTC/timezone bug found and fixed while building this**: this
database's continuous aggregates bucket in UTC regardless of session timezone
(confirmed against the live instance), but `generate_series($1::date, $2::date,
interval)` resolves to `timestamptz` — not the plain `date` its arguments suggest,
since Postgres has no `generate_series(date,date,interval)` overload — built via an
implicit `date→timestamptz` cast through the session's `Asia/Baghdad` timezone. pgx
then decodes that back into a Go `time.Time` in UTC, and formatting it with
`"2006-01-02"` silently shifted the calendar date backward by Baghdad's offset (a day
bucket meant to be "Aug 18" rendered as "Aug 17" once round-tripped through Go — caught
by `TestTrendsReport_ActiveExpiredCounts` before it ever shipped). Fixed by casting the
bucket back to `::date` in the `SELECT` list, re-entering plain-date space before pgx
ever sees a timestamptz. Documented in `trends.go`'s own comment so the next person
touching a `generate_series` day-bucket in this codebase doesn't rediscover it the hard
way. `top10Handler`/`trafficByEntityHandler`'s own "today"/"month" boundaries are
deliberately UTC-anchored (not Asia/Baghdad) for the same underlying reason — a
day-granularity rollup that already exists cannot be re-sliced to a different
timezone's midnight after the fact without silently misattributing up to 3 hours of
traffic at every boundary; using the bucket's own anchor is the only version of "today"
this data can answer exactly. Documented at the call sites, not silently deviated from.

**Live-verified** (real Postgres+TimescaleDB, WSL2, `internal/reports` package):
`TestDailyTraffic_MatchesUsagePointsSum`, `TestTrafficByEntity_UsersAndCardsNeverMix`,
`TestTop10_RanksDescendingByBytes`, `TestTrendsReport_ActiveExpiredCounts` — all four
pass on a fresh database and, after fixing two test-isolation issues found by rerunning
them back-to-back against a never-reset database (fixed-date fixtures randomized like

of an unscoped global read, matching `TestSettlementAndRevenueScopedManagerIsolation`'s
own isolation pattern), pass repeatedly under that stress too.

### FR-175 — Reconciliation: the phase's real deliverable

**A real money bug was found and fixed while building this**, and it is the single
most important thing this phase produced. `internal/billing/journal.go`'s
`postLedgerJournal`, for every wallet-mediated renewal/voucher-redeem/adjustment/
refund/manual-payment/discount, called `signedPair(acctAgentWallet, acctRevenue,
entry.Amount, …)` — the two account codes in the wrong order for this specific call
site. `signedPair`'s contract ("positive amount → Dr first arg / Cr second arg;
negative → sides swapped") is correct as written and correct everywhere else in the
file (`topup`, `commission`, the direct-cash leg all only ever see a positive amount in
practice); this is the one call site whose *normal* case (`entry.Amount = -balanceAmount`,
always negative for an ordinary spend) hits the negative branch, where the swap
silently inverted the intended direction. The result, confirmed against a live
database: **every wallet-mediated renewal credited (increased) the agent's liability
account instead of debiting (decreasing) it, and debited revenue instead of crediting
it** — a spend that should shrink both the wallet and grow revenue instead grew the
wallet and shrank revenue. After a 100,000 IQD topup and one 10,000 IQD renewal, the
journal's own wallet subledger showed a net credit of 110,000 against a real
ledger/balance of 90,000 — a 20,000 IQD divergence from a single renewal, compounding
with every renewal thereafter. Migration 0618's backfill SQL (the PL/pgSQL
re-implementation of this same rule, written independently) has the **correct**
direction, so the live dual-write path and the backfill path had been posting opposite
signs for this exact case since v4-9 shipped, and v4-9's own gate-item-3 test
(`TestJournal_DualWriteAgrees_TopupRenewRefund`, written specifically to catch this)
never reached its own assertions, because of a second, unrelated bug (below) that made
it 404 before it could check anything.

**Fixed in this phase's own commit**: the two account codes swapped in `journal.go` to
match the backfill's already-correct direction. Re-verified live: the identical
topup+renewal fixture now shows a journal wallet net of exactly 90,000.

**Six more bugs found and fixed in the same sweep**, all in

**What FR-175 does NOT claim**, stated plainly rather than glossed: a **reseller-scoped**
revenue report does not tie to a journal query, and this is by design (v2-9), not a
gap. `postLedgerJournal` books a wallet-mediated sale's Revenue credit at the manager's
own balance effect — wholesale for a reseller — while `reports/revenue.go` always sums
`payments.amount`, the subscriber's retail charge. Once reseller markup exists, these
are two different, both-correct numbers answering two different questions ("what did
the platform earn from this reseller" vs. "what did the reseller's own subscriber
pay"), and no journal query answers the retail-side question at all — there is no
journal tagging dimension for it. Margin reports (v2-9) already exist specifically to
show the wholesale/retail split; FR-175 does not duplicate that here.
