The Field→FormField migration this item's original wording anticipated **did happen this phase**, in the end. A first pass estimated the scope at 169 `<Field` instances / 104 missing `htmlFor` across 34 files (via `grep -c "<Field[^>]*htmlFor"`) and judged that too large to complete with real verification in one session. That estimate was itself wrong — the grep only matches `htmlFor` on the *same line* as `<Field`, so it miscounted as "missing" any multi-line `<Field label=... htmlFor=...>` whose attributes Prettier had wrapped, which is most of them with 2+ props. A corrected, multi-line-aware scan found the real gap was **24 instances across 6 files**, 2 more of which were separately false-flagged by a `>` inside a JSX comparison expression — the true gap was **22 instances across 5 files**, all now migrated (frontend-only, no `backend/internal` change, so this item's own scope is unaffected either way). 2 deliberate exceptions remain on `Field` (group-label cases — `NasWizardModal`'s service list and `SubscriberFormModal`'s service-type radio group — where each option/row already self-labels and FormField's one-id model doesn't apply), documented in `known-issues.md`. Zero behavior change holds for both the backend deletion and the frontend migration — the migration only threads an `id` a screen reader can use; no visible markup, styling, or interaction changed (verified: `npm run build`/`lint`/`test` all clean throughout, chunk sizes unchanged except from the added `id`/render-prop code itself).
