## What shipped (FR-160–165)

### One queue, built by relocating delivery — not duplicating it (binding rule)

The phase brief's central instruction was to build ON the existing alert-routing/quiet-hours/retry/delivery-isolation infrastructure, not beside it. That infrastructure (`internal/monitorsvc`'s `alertEngine` + `channels.go`'s senders) predates this phase and drove admin alerts by dispatching directly, synchronously, per channel. Making broadcast/transactional/alert messages truly share one queue required moving the channel-sending implementation itself into the new `internal/notify` package (the phase's actual owner of delivery from here on), not adding a second implementation beside the first:

- **`internal/notify`** (new) — `notification_outbox` (0625) is the durable queue, modeled directly on `internal/radius`'s `coa_outbox` (the phase brief's own template): `queued → sending → {sent | skipped}` or back to `queued` (retry, capped at 5 attempts with backoff) until exhausted into `failed`. `channels.go` now holds the ONLY implementation of the Telegram/email/WhatsApp/SMS senders in the codebase (moved from `monitorsvc`, SMS added new). `dispatcher.go` claims a batch per tick (`FOR UPDATE SKIP LOCKED`, crash-safe reclaim of stuck `sending` rows) and is the only caller of any sender. `templates.go`/`rules.go` back the Messages/Rules tabs. `enqueue.go` (`EnqueueEvent`/`EnqueueAlert`/`EnqueueBroadcast`) is the ONLY way anything in the codebase puts a message in front of a recipient — every caller funnels through it.
- **`internal/monitorsvc`** — `alerts.go`'s `Fire` now calls `notify.EnqueueAlert` instead of dispatching inline; `alert_events` still records every fire, but "delivery" now means "queued", with the outbox itself the truthful record of what actually sent. `subscriber_events.go`'s `handleRenewed`/`handlePaymentTicket` now call `notify.EnqueueEvent` instead of a direct WhatsApp send. `subscriber_whatsapp.go`, `channels_test.go`, `digest_subscriber_test.go`, `push_channel.go`, and `util.go` were deleted outright (their logic now lives in `notify`, or — for the day-based per-subscriber expiry reminder `digestPerSubscriber` used to send inline — was replaced by `notify/scanner.go`, driven by `notification_rules.renewal_reminder`/`expiry_notice`'s own `days_before`, editable on the Rules & timers tab, instead of piggybacking the admin `expiring_digest` alert rule's threshold). Panel Web Push (FR-54.4, a distinct pre-existing channel, not one of this phase's five) still fires directly — folding it into the queue was out of scope and would have conflated two different systems.
- **Proof, not just design intent**: `TestOneQueue_EveryEnqueuePathAppearsInOutbox` (notify, DB-gated) calls all three entry points (`EnqueueEvent`, `EnqueueAlert`, `EnqueueBroadcast`) and asserts `source IN ('rule','alert','broadcast')` all land in the same `notification_outbox` table. `TestSubscriberEvents_RenewedEnqueuesAndDispatchesWhatsAppReceipt` (monitorsvc, DB-gated, rewritten this phase) proves the full path end to end: a real Redis publish → `subscriberEvents` enqueues → one `notify.Dispatcher.Tick` call drains it → a request-capture fake receives the exact WhatsApp payload. The pre-v4-10 version of this test asserted a synchronous send; the rewrite is the architecture's own proof that the queue is real, not just a signature change.

### FR-160/FR-163 — Notification Center, six tabs (0625–0626)

`internal/notify/module.go` serves Overview (live counters + channel status), Channels (read-only health — credentials are edited through the *existing* `GET/PUT /api/v1/settings/notifications`, extended with `sms`/`whatsapp_templates` fields rather than a second config surface), Messages (versioned template editor), Rules & timers (enable/channels/`days_before`/`ignore_opt_out`/batch size/tick interval), Broadcast (`EnqueueBroadcast`, always opt-out-honouring — a one-off blast has no "ignore opt-out" escape hatch), and Outbox (filterable list, per-row inspect/retry/cancel). `frontend/panel/src/pages/notifications/NotificationCenterPage.tsx` implements all six as one tabbed page, mirroring `StatementsPage.tsx`'s established pattern.

### FR-161 — SMS channel (0627)

Generic HTTP gateway (configurable URL/method/param-mapping) plus a named-provider preset field, `smsSender` in `channels.go`. Credentials go through the **existing** `platform.SetEncrypted`/`GetEncrypted` (the same envelope NAS secrets/SMTP/Telegram/WhatsApp already use) — `settings_api.go`'s `notificationSecretFields` gained `"sms"`, no new secret storage path. Per-subscriber per-channel opt-in (`subscriber_channel_opt_ins`, migration 0627) covers `sms`/`email`; WhatsApp keeps its own pre-existing explicit-opt-in column and semantics unchanged (FR-55.3 is a Meta consent requirement, not a courtesy preference, so it is checked unconditionally regardless of `ignore_opt_out`). The panel's existing `NotificationsSettings.tsx` (Settings → Notifications) gained an SMS section; `setupapi/notify_test_send.go`'s "Send test" gained an `sms` case reusing the identical gateway-call logic.

### FR-162 — Templates

`notification_templates` (0626) is append-only and versioned exactly like the journal (0617, v4-9's own precedent): editing inserts the next version, never rewrites history, so `notification_outbox.template_version` always identifies the exact text that produced a given message. Seven events (`renewal_reminder`, `expiry_notice`, `quota_warning`, `payment_receipt`, `plan_renewed`, `payment_ticket_state`, `staff_alert`) each ship a default template in **en/ar/ku in the same migration commit** — `TestDefaultTemplates_AllEventsTrilingual` (DB-gated) asserts all 21 rows exist with no locale silently falling back to English. Rendering is a plain `{{key}}` substitution (`render()` in `templates.go`) — deliberately not a general template language, so there is no injection surface in operator-edited free text.

### FR-164 — Support tickets (0628–0629)

New `internal/support` package, tables named `support_tickets`/`support_ticket_messages` (deliberately distinct from the pre-existing `payment_tickets` — a payment-confirmation workflow, not customer support — so the two are never confused by name or by route: `/api/v1/support-tickets` vs. `/api/v1/payment-tickets`). Five statuses, three priorities, a human ticket number (`TCK-000123` via a dedicated sequence), scoped by **the existing `auth.ScopeFilter`**, reused verbatim (`ticketFilters`/`canSeeTicket` mirror `billing/tickets_api.go`'s/`ticket_attachments.go`'s identical functions line-for-line in shape, not reimplemented). Withdrawn tickets hidden by default (`include_withdrawn=true` to see them), matching the brief's "withdrawn... hidden by default."

**Internal notes never leak (the phase's most severe binding rule).** `support/public.go` is the single boundary: `PublicMessage` has no `internal` field at all — there is no wire shape an internal note's content could accidentally occupy — and `PublicMessages()` *drops* internal rows rather than masking them. Every subscriber/bot-facing function (`ListForSubscriber`, `GetForSubscriber`, `ReplyAsSubscriber`) is built through it; the full internal+public thread (`listMessages`) is reachable only from the staff-only, `support.view`-gated HTTP handlers. `internal_note_leak_test.go` is a pure unit test (no DB) with four cases: a mixed thread's public output contains only the three public messages, by id; the JSON serialization of that output contains none of the internal bodies or ids anywhere in the byte stream (not just structurally — a `strings.Contains` sweep over the marshaled wire bytes); `PublicMessage`'s own JSON never even mentions the word "internal"; an all-internal thread yields zero public messages, not an error.

`frontend/panel/src/pages/support/SupportTicketsPage.tsx`: filter chips (status/priority/scope/search), queue table, detail modal with the thread (internal notes visually distinct — amber background + a badge), a reply box with an explicit "Internal note" `Switch` (defaulting off, never inferred from role), status-lifecycle buttons, and withdraw.

### FR-165 — Telegram self-service bot (0630)

New `internal/telegrambot` package, running inside `hikrad-monitor` (the pre-existing internet-dependent background process — the same one the alert engine already lives in — so the bot's absence structurally cannot affect RADIUS auth or accounting, NFR-7). Account linking: `telegram_links` (0630) holds a one-time 6-digit code (`IssueLinkCode`, 10-minute TTL) issued by a new authenticated portal endpoint (`POST /api/v1/portal/telegram/link-code` in `portalapi` — the portal *button* that calls it is v4-11's UI, out of this phase's scope per the brief, but the backend seam it needs is delivered now) and consumed by the bot's `/link <code>` command, which binds the chat to exactly one subscriber (a chat already linked to someone else is refused, never silently re-bound). Commands: `/usage`, `/invoices`, `/tickets`, `/newticket <text>` (calling `support.CreateForSubscriber`/`ListForSubscriber` directly — no HTTP hop, same process, same DB pool), `/help`.

**Degrades gracefully, never grows an unbounded queue (gate item 12, NFR-7).** The bot is pull-based by construction — it long-polls Telegram's `getUpdates`, so there is nothing buffered on HikRAD's own side for Telegram-unreachable to pile up in; a failed poll just retries with exponential backoff (capped at 30s). No bot token configured → the poll loop degrades to a near-zero-cost recheck every 60s rather than spinning. Interactive command replies (`bot.reply`) are a synchronous response inside an existing conversation — the same posture as an HTTP handler's response body — not a queued "message"; only the bot's *proactive* notifications (a ticket reply, a renewal reminder) would traverse the outbox, via the same `notify.EnqueueEvent` every other channel uses once a subscriber is linked (the linked `chat_id` becomes the `telegram` channel's resolved address in `resolveSubscriberChannel`).

## Security review

- **Internal note leak**: the phase's own named highest-severity risk — addressed structurally (§ above), not by convention, and tested at the byte level.
- **SQL injection**: every new query in `notify`/`support`/`telegrambot` uses parameterized placeholders; the one string-built fragment (`ticketFilters`'/`OutboxFilter.where`'s `$%d` placeholder numbering) builds argument *positions*, never argument *values*, into the SQL text — the same pattern `billing/tickets_api.go`'s `ticketFilters` and `radius/coa_outbox_store.go`'s `outboxFilter.where` already established.
- **Ticket scoping (IDOR)**: `canSeeTicket` mirrors `billing/ticket_attachments.go`'s `canSeeTicket` exactly — an unscoped caller sees everything, a scoped caller only rows whose subscriber's `owner_manager_id` matches their own id. `TestScoping_AgentSeesOnlyOwnSubscribersTickets` (DB-gated) proves it against two real managers/subscribers/tickets, both directions (scoped sees only their own; unscoped sees both).
- **Encryption at rest (gate item 3)**: `TestSMSChannelSecret_EncryptedAtRest` (DB-gated) doesn't assume the encryption service works — it stores an SMS config with a real-looking API key, then reads the **raw** `settings.value` column directly via SQL, asserts the plaintext key and even the field name `api_key` appear nowhere in it, asserts the stored value is valid base64 ciphertext (not the plain JSON shape), and only then round-trips it back through `GetEncrypted` to confirm it still decrypts to the original value.
- **Bot identity binding**: `consumeLinkCode` checks for an existing link on the *chat* before accepting a new code, so a already-linked chat can never be silently re-bound to a second subscriber (`errAlreadyLinked`); a subscriber can re-request a code (overwriting their own pending one) without limit, but each code is single-use (cleared to `NULL` on success) and time-boxed.
- **`auth.ScopeFilter` reused, not reimplemented** (kickoff instruction, honored literally): grepped for any new `owner_manager_id` filtering logic outside `ticketFilters`/`canSeeTicket` — none exists; both functions are structurally the same shape as billing's pre-existing ones, not parallel reinventions.

## Deliberate scope decisions

- **Portal UI (v4-11's job) is genuinely absent.** This phase delivers the backend seams v4-11 will consume — the telegram-link-code endpoint, the public ticket functions — but no portal screen calls them yet. Explicitly out of scope per the phase brief ("Not in: the portal's ticket and preference screens").
- **Quota warning's scanner query is a straightforward join, not optimized for scale.** `scanQuotaWarning` sums `usage_points` since `quota_cycle_anchor` per metered subscriber on every hourly tick — correct (mirrors `accounting/quota.go`'s own live-derivation posture) but O(subscribers × usage rows); a large deployment may want this pre-aggregated later. Flagged here rather than silently shipped as if it were tuned.
- **Admin WhatsApp alert templates now go through the same approved-template catalog subscriber messages use**, rather than the old single free-text `notifications.whatsapp.template`/`lang` fields. This is a real (small) contract narrowing: an operator who had an admin WhatsApp alert channel already configured needs to register a `staff_alert` entry in the template catalog for it to keep working, since Meta requires pre-approved templates outside a session window either way. The old fields are silently ignored (JSON decode into the new, smaller struct just drops them) rather than erroring — flagged here, not left for someone to discover as an unexplained regression.
- **The Broadcast tab's subscriber picker is a raw ID textarea**, not a search-select filtered by plan/status. A real search-and-select component is a natural follow-up; the phase's own gate items don't test the picker UX, only that a broadcast enqueues correctly once IDs are supplied.
- **The bot has no rich formatting, no inline keyboards, no multi-step conversations** — every command is a single message in, a single reply out. FR-165's acceptance list (link, usage, invoices, ticket create/follow) is met without needing either.
- **`notification_rules.batch_size`/`tick_interval_seconds` are stored and editable but not yet read by the running dispatcher worker.** The dispatcher's `Tick(ctx, batchSize)` accepts a caller-supplied batch size and `Run` passes its own fixed package constants (50 rows / 5s) — the same shape `coa_dispatcher.go` uses for the whole CoA queue, and the one gate item 7 actually tests (a single global throttle respected under a 1,000-message broadcast, proven by `TestThrottling_BatchSizeRespectedUnderLargeBroadcast`). Per-*rule* overrides (a critical-priority ticket's notifications draining faster than a bulk promotional broadcast, say) would need either a per-rule ticker or a dynamic effective-batch-size computed each tick — flagged as a real, scoped-out enhancement, not silently implied by the fields existing in the schema and UI.
