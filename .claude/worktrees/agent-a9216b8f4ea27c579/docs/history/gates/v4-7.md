## What shipped (FR-144–149)

- **Migrations 0610–0613** — renumbered from the phase brief's stated
  0609–0612 budget: `ls backend/migrations | sort -V | tail` at kickoff
  showed the real max was already `0609` (v4-6's own renumbered last
  migration, itself uncommitted in the working tree), so the master plan's
  "next free number, budgets are not reservations" rule moved the whole
  range up by one — exactly the same renumbering v4-6 itself did against
  v4-5. `0610` (`nas_setup_wizard_state`) is the wizard's resumability
  substrate: one row per NAS, `step` + `form_data` jsonb, upserted wholesale
  on every step transition. `0611` extends `nas_services` with the FR-145
  per-instance parameters and FR-149's IPv6 fields, adds the new
  `nas_wan_uplinks` object type (mirroring `nas_services.management_mode`
  exactly), and adds `subscribers.ipv6_static_prefix` — a cross-domain
  column addition from this module, the identical precedent FR-64 already
  established. `0612` (`nas_firewall_snapshots`) is the auto-revert safety
  net's evidence table. `0613` (`nas_hotspot_pages`) tracks design vs.
  pushed version and pushed RouterOS version independently.

- **The central contract, extended not replaced** — every new object type
  (bridge, bridge ports, DNS, NTP, WAN uplinks, firewall rules, IPv6
  pool/profile attachment) is planned through the *exact same*
  `vendor.PlanItem`/`PlanConflict`/`AutoSetupPlan` vocabulary FR-56/66/67
  already established, and applied through the *exact same* generic
  `ApplyAutoSetup` executor (proven generic already by FR-108's pool push
  reusing it, and reused again here rather than re-verified from scratch).
  New vendor files: `mikrotik_wizard.go` (`PlanWizard`, `DetectWizard`, plus
  per-step planners `planBridgeSetup`/`planDNSSetup`/`planNTPSetup`/
  `planFirewallWizard`), `mikrotik_wan.go` (`ReadWANUplinks`/
  `PlanWANUplink`), `mikrotik_firewall.go` (`ReadFirewallRules`/
  `PlanFirewallChange`/`SnapshotFirewallRules`), `mikrotik_update.go`
  (`ReadUpdateInfo`/`CheckForUpdates`/`ApplyRouterUpdate`),
  `mikrotik_hotspot_page.go` (`PushHotspotPage`), `mikrotik_ipv6.go`
  (`PlanIPv6`). `PlanWizard` itself does not reimplement RADIUS wiring or
  server creation — it calls the *existing* `PlanAutoSetup`/`PlanService`
  internally and folds their `Items`/`Conflicts` into the combined review
  plan, so the wizard and the standalone auto-setup/service-create flows
  can never describe two different desired states for the same router
  object.

- **FR-144 wizard backend** (`wizard_api.go`, `wizard_store.go`) —
  `GET/PUT /nas/{id}/wizard/state`, `POST .../wizard/detect` (read-only,
  reuses `ReadBridges`/`ReadDNS`/`ReadConfig`/`DiscoverServices`/
  `ReadWANUplinks` rather than a second read path), `POST .../wizard/plan`
  and `.../wizard/apply` (hash-gated, `wizardPlanHash` mirrors
  `planHash`/`serviceHash`/`poolPushHash`'s exact tamper-safety reasoning).
  A successful apply persists services/pools/IPv6 config to HikRAD's own
  tables (`persistWizardApply`, mirroring `serviceApplyHandler`'s
  post-processing) and marks the wizard state completed.

- **FR-145 service tabs backend** — `PUT /nas/{id}/services/{serviceId}/params`
  persists the extended per-service metadata (interim override, hotspot
  user profile, DHCP range, IPv6 fields) with no router write (a documented
  scope decision — see below). The Internet tab (`wan_api.go`,
  `wan_store.go`) gives WAN uplinks their own `management_mode`-gated
  plan/apply/adopt trio, identical in shape to FR-108's pool push.

- **FR-146 firewall backend** (`firewall_api.go`, `firewall_store.go`) —
  `POST .../firewall/apply` snapshots the pre-change value of every rule its
  plan is about to `/set` (via `SnapshotFirewallRules`, called **before**
  `ApplyAutoSetup` writes anything — the ordering the whole mechanism
  depends on) and schedules a 5-minute revert deadline; a new goroutine
  (`startFirewallRevertWorker`, started from `module.go` alongside the
  existing enforcement/TOD/limits/device workers, polling every 15s) restores
  the stored revert sentences for any unconfirmed snapshot past its deadline.
  `POST .../firewall/{snapshotId}/confirm` cancels the pending revert.
  Editing a rule without the `hikrad-auto` comment tag is a non-resolvable
  conflict — router-managed rules refuse editing until adopted, the same
  posture as an un-adopted `nas_services` row.

- **FR-147 Update tab backend** (`update_api.go`) — read/report by default;
  apply gated on a new `nas.update` permission (added to
  `internal/auth/roles.go`'s catalog), deliberately separate from
  `nas.edit`/`nas.reboot` since installing firmware is neither.

- **FR-148 hotspot login page backend** (`hotspot_page_api.go`,
  `hotspot_page_store.go`) — three modes; the branded template renders from
  `platform.LoadIdentity` (never a second branding read, per the phase
  brief's explicit instruction); `PushHotspotPage` writes to router flash
  via `/file/add`/`/file/set` (a RouterOS 7.x API mechanism — the ROS 6.x gap
  is a known, documented limitation, see below); staleness is computed as
  two independently-tellable reasons (`unpushed_edit` vs.
  `ros_upgraded_since_push`), never one generic warning.

- **FR-149 IPv6 backend** — `vendor.PlanIPv6` builds an `/ipv6/pool` from an
  ISP-delegated base prefix and attaches it to the service's PPP profile's
  `dhcpv6-pd-pool`. The RADIUS reply-side plumbing for a static per-subscriber
  pin is wired (`AuthView.DelegatedPrefix`, `policy.go`'s emission tail,
  `IntentDelegatedPrefix` → RFC 3162 `Framed-IPv6-Prefix` mapped in both the
  Go CoA adapter and `authorize.pl`) and inert-by-default (proven by the full
  pre-existing `internal/radius` suite passing completely unmodified with the
  new always-empty field). The subscribers-package loader that would actually
  populate `DelegatedPrefix` from `subscribers.ipv6_static_prefix` was **not**
  written this phase — flagged as an open known-issues row, not silently
  claimed. Dynamic (non-pinned) delegation is unaffected: it is router-native
  via the PPP profile attachment and needs no RADIUS attribute at all.

- **Panel** — `SetupWizardPage.tsx` (routed `/nas/{id}/wizard`, linked from
  each NAS card's "Setup wizard" button): 10 visible steps (detect → bridge →
  bridge ports → DNS → NTP → Internet → RADIUS → services → details/firewall
  → review & push), one accumulated `WizardFormData` object PUT to
  `/wizard/state` after every Next **and** Back so a half-finished run
  survives a browser close and Back can never discard a later step's already
  -entered values. `InternetTab.tsx`, `FirewallTab.tsx` (with a full-width,
  danger-toned, live-ticking countdown banner for a pending auto-revert —
  gate item 11's UI half), `UpdateTab.tsx` (double-confirm, mirroring
  `GeneralTab.tsx`'s Reboot pattern exactly) all wired into `DevicePage.tsx`'s
  tab groups. `HotspotPageModal.tsx` reachable per-hotspot-service from
  `NasListPage.tsx`'s services sub-list. A new shared `components/PlanPreview.tsx`
  (factored out of the pre-existing `NasAutoSetupModal.tsx`/
  `ServiceProvisionModal.tsx` duplication, per this phase's own explicit
  instruction) renders the literal-command items list (gate item 5) and the
  keep/update/abort conflict resolution (gate item 7, abort-default) in
  every one of the five new write surfaces that need it.

## Deliberate scope decisions (and one interrupted delegation, disclosed)

- **A background agent tasked with the frontend build failed partway
  through this session** with `session limit · resets 6:50pm (Asia/Baghdad)`
  — an account-level rate limit, not a bug in its work. What it had already
  delivered before stopping (the five new API clients, the shared
  `PlanPreview.tsx` component, and a complete `InternetTab.tsx`) was real,
  correctly typed, and already followed the codebase's established patterns
  — confirmed by building and lint-checking it, not merely trusting the
  agent's own report (which never arrived; the task notification carried
  only the failure). The remainder of the frontend (`SetupWizardPage.tsx`,
  `FirewallTab.tsx`, `UpdateTab.tsx`, `HotspotPageModal.tsx`, all wiring and
  i18n) was completed directly in this session afterward, on top of that
  foundation, rather than re-delegated.
- **FR-145.1's extended service parameters have a working backend
  (`PUT .../services/{serviceId}/params`, persisted, round-trip tested by
  the type system) and a working API client, but no panel form consumes it
  yet.** An explicit, undelegated gap — building it would have meant either
  extending the already-large `ServiceProvisionModal.tsx` or a new small
  form, and time ran out before either was started. The fields are inert
  metadata (see the next point) so the gap has no correctness consequence,
  only a completeness one.
- **The interim-interval/hotspot-user-profile/DHCP-range fields persist but
  do not yet drive a router write** — `vendor.PlanService` was not extended
  to act on them this phase (logged as an Open known-issues row). IPv6
  fields on the same row are the exception: they DO reach the router,
  through the wizard's `PlanIPv6` step specifically, not through the params
  endpoint.
- **RouterOS 6.x cannot receive a pushed hotspot login page** through this
  phase's `PushHotspotPage` (the RouterOS API has no file-content-write
  sentence on that version) — a scope decision made at kickoff (adding an
  FTP transport for one write path would be a second RouterOS client,
  forbidden by FR-17.1/FR-56.4), logged as an Open known-issues row with the
  router's own error surfaced to the operator rather than a silent no-op.
- **The wizard's bridge-port and WAN-interface fields are hinted text
  inputs, not discovery-fed dropdowns** — unlike the Internet tab's create
  form (which DOES use a `Select` populated from `getInterfacesTab`, with a
  free-text escape hatch, matching gate item 10 exactly) and every FR-67
  service form before it. A scope decision under time pressure, not an
  oversight: gate item 10 is met by the Internet/service forms, partially
  met by the wizard.
- **FR-149's static per-subscriber IPv6 prefix pin has no populating loader**
  — see "What shipped" above and the new known-issues row.
