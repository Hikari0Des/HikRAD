# v4-5 gate result — Subscribers, counters & card groups

**Status: GREEN with real database/Redis verification this session** — unlike
v4-2/v4-3/v4-4's sandboxes, this session had a live (throwaway, isolated)
Postgres + Redis available via Docker, so every DB-gated test below was
**actually executed against real infrastructure**, not merely self-skipped.
That changes the character of this gate result: several real bugs were
found and fixed by running tests for real rather than reading code (listed
under "Bugs this session's live testing caught" below) — direct evidence of
what "run it, don't just read it" buys. The packet-harness leg (gate items
1/6/10's live-NAS half) still could not run — no FreeRADIUS binary in this
sandbox — and is proven instead at the policy-engine layer, the same posture
v4-4's own gate took and the same layer that actually decides accept/reject.

## What shipped (FR-133–138)

- **FR-134 — Counter split**, done first per the kickoff instruction.
  `subscriber_billing_counters` (migration 0602) is the lifetime table:
  incrementally maintained (not derived-live, unlike every other usage
  figure in this codebase) because a lifetime sum over an ever-growing
  history would get slower every day forever — the one deliberate exception
  to "derive, never store-and-edit," documented as such in the migration and
  code comments. Its **only** writer is `internal/accounting`
  (`billingcounters.go`), incrementing bytes in the same transaction as the
  `usage_points` row they derive from, and connected-seconds once at Stop
  (**including** a reaper-synthesized stop — a real gap the reaper wasn't
  originally crediting, found and fixed this session). `subscriber_counters`
  (v4-4) stays the resettable side; a renewal now also resets
  `uptime_cycle_anchor` there (`billing/renew.go`), completing what v4-4's
  own gate note deferred to this phase. **Enforcement of "no reset path
  writes the lifetime table"** is a static test
  (`TestLifetimeBillingCountersHaveExactlyOneWriter`,
  `internal/subscribers/billingcounters_guard_test.go`) that greps the whole
  backend module for a write statement against the table outside
  `internal/accounting` — not a convention, a compile-time-adjacent check.
- **FR-133 — Batch/numbered creation.** `POST /api/v1/subscribers/batch`
  (`internal/subscribers/batch.go`) structurally mirrors `bulk.go`: the same
  in-memory job registry, the same per-row-independent execution loop, the
  same detached-context audit writes. `usernames()` is the ONE username
  generator both dry-run and execute call, so "dry-run matches the result
  exactly" (gate item 3) holds by construction. The licence cap
  (`platform.EvalSubscriberCap`) is checked once, before any row is written,
  against the batch's true would-create count (collisions excluded). Three
  invoicing modes — none/each/batch — the "each" and "batch" modes route
  through a **new seam** (`subscribers.Invoicer`, implemented in
  `billing/batch_invoice.go`) rather than a duplicated money path: "each"
  calls THE renewal function every other renewal source already converges
  on; "batch" posts one aggregate ledger entry, reusing
  `lockBalance`/`insertLedger`/`recomputeBalance` exactly as
  `billing/voucher.go`'s own batch-generation debit already does. Generated
  passwords are carried on the job snapshot once (`bulkJob.Passwords`),
  never persisted in the clear, mirroring vouchers' "exists once" posture.
- **FR-135 — Subscriber list depth.** `GET /api/v1/subscribers` now attaches
  a `limits` map (`internal/subscribers/limitprogress.go`) batched across
  the whole page via `LEFT JOIN LATERAL` — one round trip, not N — carrying
  quota/uptime/daily used-vs-limit, days remaining, and a plan-swap badge.
  The badge re-derives the identical frozen evaluation order (expiry → quota
  → uptime → daily) `radius/limits.go`'s `evaluateLimits` uses, so it names
  the same limit RADIUS would actually be acting on — a read-only display
  projection, not a second decision-maker (nothing here rejects/throttles
  anyone). The panel gained a "Limits" column (`LimitProgressCell.tsx`:
  compact bars + days-remaining + swap badge), a client-side online/offline
  filter (one-shot live-session snapshot, `UserListPage.tsx`), and the
  existing status/profile/owner/expiring filters were left untouched.
- **FR-136 — Card groups (Decision 65).** New `internal/cards` package.
  `card_groups` (0603) carries its own rate/transfer/uptime/expire-after-
  first-login/shelf-date settings — deliberately not a profile, since a
  profile governs long-lived subscriber accounts and a card group governs a
  disposable printed batch. `cards` (0604) are hashed-at-rest exactly like
  vouchers (`hash.go` duplicates the identical sha256-of-normalized scheme
  on purpose — this is what makes migration 0605's byte-for-byte code
  preservation possible). **Auth-time, cards evaluate through the
  UNMODIFIED v4-4 engine**: `radius/cardauth.go` is a seam
  (`CardAuthenticator`, wired from `internal/cards`) that mirrors
  `radius/voucher.go`'s exact shape; `cards/auth.go`'s
  `AuthenticateCard` builds a `radius.AuthView` — mapping the group's
  transfer limit onto `QuotaExhausted`, uptime onto
  `UptimeLimitSeconds`/`UptimeUsedSeconds`, and **folding both
  expire-after-first-login AND the shelf date onto the single
  `ExpiresAt` field by taking whichever is earlier** — and hands it to
  `policy.go`'s existing `decide()`/`evaluateLimits`, which makes every
  accept/reject decision exactly as it does for a subscriber. `cards/
  no_second_engine_test.go` statically greps the package for the shape of a
  second implementation (a `radius.Reason*` reference, a hand-built
  `authorizeResponse`) and fails if either appears — gate item 10's binding
  rule enforced as a test, not a promise. Group actions (enable/disable-all,
  extend shelf date, add-more cards, duplicate-with-fresh-codes, per-card
  reset restoring `active` from `exhausted`) are all implemented and
  DB-tested. Migration 0605 migrates every existing voucher batch into a
  `source='legacy_voucher'` card group **additively only** — zero UPDATE/
  DELETE against `vouchers`/`voucher_batches`, `code_hash` copied verbatim
  — so the original voucher redemption path is provably untouched (see gate
  item 8 below). `sessions`/`usage_points` gained a nullable `card_id`
  column (0604), resolved in `internal/accounting` alongside (never instead
  of) `subscriber_id` resolution, additive and best-effort.
- **FR-137 — Printing and tracking.** `POST /api/v1/cards/groups/{id}/print`
  renders a branded, print-ready HTML page (logo + name from the same
  `platform.LoadIdentity`/`ReadLogoBytes` resolver `radius/hotspot.go`'s
  login page already uses) that the operator's own browser turns into a PDF
  via its native print-to-PDF dialog — the same pattern `billing/receipt.go`
  already established for receipts, since no PDF-rendering dependency exists
  anywhere in this backend and this phase does not introduce one. Printing
  takes the plaintext codes as request input (the only time they exist,
  immediately after generation) rather than pretending to recover them from
  storage. `GET /api/v1/cards/groups/{id}/usage.csv` exports per-card
  usage/state/first-login for the "tracked distinctly" requirement.
- **FR-138 — Legacy importers.** Extends the FR-6/FR-111.3 wizard rather
  than forking a fourth import path, per the binding instruction: a Radius
  Manager/Super Speed Radius MySQL dump (`internal/importer/sqldump.go` —
  a purpose-built `INSERT INTO … VALUES …` extractor, not a SQL parser) or a
  Pro Radius XLSX (`internal/importer/xlsx.go` — a minimal, stdlib-only
  zip+XML reader, no new dependency) is converted to the **identical
  canonical CSV text** a plain SAS4 upload already produces, at the upload
  edge (`api.go`) — everything downstream (mapping, dry-run, execute,
  per-row independence) is unmodified and unaware of the source format.
  Migration 0606 adds `import_batches.source_system` for traceability and to
  drive the format-specific preset guess. Best-effort presets for all three
  systems are provided for both entities (subscribers/profiles) — real
  schemas were not available to verify against, the same documented
  uncertainty the existing SAS4 preset already carries.

## Bugs this session's live testing caught (fixed, not just noted)

Running real Postgres+Redis this session (unavailable to v4-2/v4-3/v4-4's
sandboxes) surfaced concrete defects no amount of re-reading would have —
this is the strongest evidence this phase's own correctness claims are
grounded in execution, not inspection:

1. **`cards/create.go`'s `createGroup` passed `insertCards`' `want` and
   `codeLength` arguments in the wrong order** — every group would have
   generated the wrong NUMBER of codes at the wrong LENGTH (a 5-count,
   10-length request silently produced 10 codes of length 5). Caught by
   `TestCreateGroup_GeneratesRequestedCount` failing with "codes = 10, want
   5"; fixed; the exact same call inside `duplicateGroup` was fixed for
   free since it goes through `createGroup`.
2. **`cards/store.go`'s `getGroup` never attached card-state counts** — a
   freshly created group's own `CardCount`/`UnusedCount` in the API response
   read as zero even though the cards existed. Caught by the same test;
   fixed by having `getGroup` run the same `attachCardCounts` batch query
   `listGroups` already used, on a one-element slice.
3. **The reaper (`accounting/reaper.go`) never credited lifetime connected-
   time for a session it closed itself** (a NAS/server that stopped hearing
   from a session before a clean Stop arrived) — only a clean Stop credited
   `subscriber_billing_counters.lifetime_session_seconds`. A subscriber
   whose sessions were mostly reaped (a flaky link) would have silently
   under-counted lifetime uptime forever. Fixed by having `reapSession`
   credit the span it closes, proven by
   `TestLifetimeCounters_ReaperCreditsClosedSession`.
4. **A pre-existing, unrelated bug in `internal/billing/currency_gate_test.go`**
   (`_, agentID := e.seedAgent(t)` discards the id and keeps the token) was
   found while running the FULL suite for real — logged in
   `docs/ops/known-issues.md` rather than fixed (out of this phase's
   domain), since this file has apparently never run against a live
   database in any prior phase either.
5. **A pre-existing, unrelated license-grace-state bug** (four tests across
   `internal/platform` and `internal/platform/setupapi` expect `grace`,
   observe `valid`) was found the same way and logged, not fixed (license/
   activation is sub-PRD 01's / v4-2/v4-3's domain).

Items 4–5 are NOT v4-5 regressions — both reproduce identically on a
completely fresh database with zero v4-5 code or migrations present,
confirmed by re-running against a throwaway pre-v4-5 database before
logging them.

## What was written and designed correctly, but not run against live hardware

- **The packet harness** (`backend/test/harness/`) was not extended with
  card/batch/limit-progress cases this session — same reasoning v4-4's own
  gate gave: the harness needs a live FreeRADIUS this sandbox does not have,
  and the policy-engine-level tests (`cardauth_test.go`) exercise the exact
  function (`engine.decide()`) the harness's wire protocol sits on top of.
  Gate item 10's "harness verifies a card hitting each limit" is proven at
  that layer, not the wire layer.
- **Mid-session enforcement for a live card.** Unlike a subscriber, a
  card-authenticated session is not walked by `radius/limitsworker.go`'s
  continuous sweep (that worker resolves views through the subscriber
  loader only) — a card that crosses its limit mid-session is caught on its
  **next** authentication attempt (every Access-Request re-evaluates live
  usage), not disconnected immediately via CoA. This is a deliberate scope
  cut, not an oversight: extending the worker to track card-authenticated
  live sessions (which carry no `subscriber_id` to key live state by) is a
  meaningfully larger change than this phase's card-groups-and-printing
  scope, and nothing in the phase brief's gate items requires mid-session
  card enforcement specifically (item 6 is phrased as "hitting each limit,"
  proven at re-auth). Flagged here rather than silently shipped.
- **The legacy-system presets** (`radius_manager`, `super_speed_radius`,
  `pro_radius` column-name guesses in `internal/importer/preset.go`) are
  best-effort, unverified against real exports from those products — the
  identical, already-documented uncertainty the SAS4 preset itself carries
  (sub-PRD 04 §7's open question). The ENGINEERING mechanism (dump/XLSX →
  canonical CSV, then the existing mapping UI) is real and tested; the
  specific column names an operator's actual export uses may differ and are
  confirmed/adjusted in the mapping step exactly like SAS4's.
- **Printing is HTML for the operator's own browser print-to-PDF**, not a
  server-generated PDF binary — consistent with the only precedent in this
  codebase (`billing/receipt.go`) and explicitly not a new dependency.

## Deliberate scope decisions

- **Card session-limit enforcement was not built** — the phase brief's field
  list for card groups (rate, transfer, uptime, expire-after-first-login,
  valid_until) never names a simultaneous-session cap, unlike subscribers'
  FR-5. `AuthView.SessionLimit` is left at its zero value for cards, which
  `sessionLimitReject` already treats as "unlimited" — no new logic needed,
  and no gate item calls for it.
- **Legacy vouchers keep their ORIGINAL redemption mechanism entirely** —
  they do not become hotspot-login-capable cards. Decision 65 asks for a
  unified LISTING ("migrate into synthetic groups"), not a unified
  RUNTIME mechanism; vouchers fund a subscriber renewal (operator/portal
  redeem), cards ARE the login credential. Building a second runtime path
  for legacy codes to also log in directly was judged out of scope and
  needlessly risky against printed stock in the field — the migration is
  provably additive-only (gate item 8) specifically because it never
  touches the table the real guarantee depends on.
- **Card group settings have no configurable exhaust actions** (no
  `throttle`/`switch_plan`/`expired_pool` for cards, unlike profiles' four-
  way FR-130 set) — every card limit resolves to `block`. The phase brief's
  field list never mentions per-limit actions for cards, and a prepaid
  hotspot card running out is the SAMM-modeled "card is spent" case, not a
  plan swap.
- **Batch creation's "invoice each" mode creates the subscriber `disabled`
  with `disabled_reason='pending batch invoice'` until the invoicing call
  succeeds**, rather than `active` with no expiry — a subscriber that was
  never successfully invoiced must never look indistinguishable from one
  that was (an invoicing failure is reported as a per-row failure, the
  subscriber row itself is not rolled back, matching "one collision does
  not roll back the rest").
