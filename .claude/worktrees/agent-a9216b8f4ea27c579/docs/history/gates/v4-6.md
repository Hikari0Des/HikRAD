## What shipped (FR-139–143)

- **Data layer (migrations 0607–0609)** — renumbered from the phase brief's
  stated 0606–0608 budget: `ls backend/migrations` at kickoff showed the real
  max was already `0606` (v4-5's last migration), so the master plan's
  "next free number, budgets are not reservations" rule moved the whole range
  up by one. `device_metrics` (0607, 1-day chunks, 7-day compression, 90-day
  retention) is the monitor grid's and Overview tab's sole read source.
  `device_interfaces` + `interface_traffic` (0608) split current-state
  (upserted in place, carrying the worker's own byte-counter bookkeeping so it
  can derive a bps rate from two consecutive reads with no second table) from
  rate history (a proper hypertable). `device_config_cache` (0609) is one row
  per `(nas_id, object_class)` for the five tabs with no dedicated table
  (General/Bridge/VLAN/IP/DNS), hashed with the same deterministic-digest
  technique `autosetup_api.go`'s `planHash` already established.
- **Vendor adapter extension** (`internal/radius/vendor/mikrotik_device.go`,
  new) — ten read-only methods added to `Adapter`
  (`ReadDeviceMonitor`, `ReadInterfaces`, `ReadGeneral`, `ReadBridges`,
  `ReadVLANs`, `ReadIPTab`, `ReadDNS`) plus the phase's two action methods
  (`Reboot`, `Ping`), all through the existing `ROSConn`/`vendor.DialROS`
  transport (FR-56's) — no second RouterOS client. Every read degrades
  section-by-section on a missing router feature (a bridge-less router simply
  reports no bridges) rather than failing the whole call.
- **Device worker** (`internal/radius/device_worker.go`, new) — started from
  `module.go`'s `Register` alongside the pre-existing enforcement/TOD/limits
  sweeps (`go m.startDeviceWorker(ctx)`), on a 60 s ticker reusing
  monitorsvc's existing SNMP-probe cadence rather than a new setting. Samples
  every enabled NAS with saved API credentials once per tick, one router
  login covering every FR-139–143 data slice. A dial/read failure marks the
  NAS unreachable in `device_metrics` and leaves every cached tab exactly as
  it was — `writeDeviceCache`'s `reachable=false` branch only ever updates the
  reachable flag and `read_at`, never blanks `data`.
- **HTTP surface** (`internal/radius/device_api.go`, new) — `GET
  /api/v1/nas/monitor` (FR-139), `GET /api/v1/nas/{id}/device/{tab}` for
  `tab ∈ {overview, interfaces, general, bridge, vlan, ip, dns}` (FR-140,
  frozen `{data, read_at, stale, ownership}` shape), `POST
  /api/v1/nas/{id}/device/refresh` (fires the worker for one NAS in a
  background goroutine and returns immediately — never blocks the request on
  the router, keeping the explicit "refresh now" action compliant with the
  same no-synchronous-call contract as the read tabs), `POST .../reboot` and
  `POST .../ping` (FR-142, the phase's two real exceptions — genuine
  synchronous router calls, gated as such). Reboot is gated on a new
  `nas.reboot` permission (added to the backend catalog in
  `internal/auth/roles.go` and the frontend's `PERM_NAS_REBOOT`), kept
  separate from `nas.edit` by design, admin-only by default (not granted to
  the built-in operator/agent roles), audited via `auth.Audit` (reads the
  actor from context), and refused `422 no_api_credentials` when HikRAD holds
  no saved API credentials for the NAS — the schema's only "the operator has
  taken responsibility for this router" gesture, standing in for the brief's
  "refused where ownership is not established."
- **Ownership badging** — computed server-side, never inferred client-side.
  Bridge/VLAN/Interfaces/DNS/Overview badge `router` unconditionally (nothing
  in v4-6 ever creates any of those objects — that arrives with v4-7's write
  surface). The IP tab's DHCP servers are the one legitimate `system` case: a
  server whose `address-pool` name matches an existing `system`-mode
  `ip_pools` row (FR-108, `systemOwnedPoolNames` in `device_worker.go`)
  badges `system`.
- **Panel** — `DeviceMonitorPage.tsx` (the grid, routed `/nas/monitor`,
  linked from the sidebar's Network group and from each NAS card),
  `pages/nas/device/DevicePage.tsx` (the shell: three tab groups —
  Monitoring/Manager/Network — mirroring `SettingsPage.tsx`'s nested-route
  pattern), one component per tab (`OverviewTab`, `InterfacesTab`,
  `GeneralTab`, `BridgeTab`, `VlanTab`, `IpTab`, `DnsTab`), a shared
  `DeviceTabShell` for the ownership badge / staleness marker / refresh
  button / "no credentials yet" / "never sampled" states so all seven tabs
  share one chrome instead of seven copies, `OwnershipBadge`/`StaleBadge`
  components, and two inline-SVG charts (`DeviceHistoryChart` for CPU/mem/
  session history, `DeviceTrafficChart` for per-interface rx/tx) built
  exclusively on v4-1's `chart-1`…`chart-8` tokens — no raw color anywhere,
  confirmed by `scripts/lint-no-raw-palette.sh` passing clean. General's
  reboot control is double-confirmed via two sequential `Modal` steps before
  the single API call fires.

## Deliberate scope decisions

- **The monitor grid's "monitor" rows** (FR-60's generic `monitored_devices`)
  surface reachability only, sourced from the existing ICMP-derived
  `health_probes` table — no CPU/memory/session-count fields, since those are
  RouterOS-API-specific and genuinely inapplicable to a generic device. This
  reads `monitored_devices`/`health_probes` directly via SQL from
  `internal/radius`, mirroring the exact cross-domain-table-read precedent
  `monitorsvc/target.go` already established in the opposite direction
  (reading `nas` from `monitorsvc`) — not a new coupling pattern.
- **A NAS without saved API credentials is silently skipped by the worker**,
  never probed some other way. Every other router-facing feature in this
  codebase (FR-56/62.6/65/108) already draws this exact line; the panel
  surfaces it as an explicit `no_api_credentials` state per tab rather than
  an infinite spinner.
- **`Reboot`'s "ownership" refusal condition is "no saved API credentials,"**
  not a dedicated per-NAS "adopted" flag — the schema has no such flag for a
  NAS record itself (only `nas_services`/`ip_pools` carry `management_mode`,
  and those are per-object, not per-NAS). Saving API credentials is the only
  consent gesture that exists; documented as an interpretation, not
  discovered in the brief verbatim.
- **IP-tab ownership badging is scoped to DHCP servers only**, not extended
  to static addresses or DHCP-client rows — the phase brief's IP tab
  enumerates "static addresses, DHCP client, DHCP server" without singling
  out pool ownership beyond the DHCP-server/pool-name relationship FR-108
  already models; badging static addresses would have required inventing an
  ownership concept for objects HikRAD has never owned in any phase.
