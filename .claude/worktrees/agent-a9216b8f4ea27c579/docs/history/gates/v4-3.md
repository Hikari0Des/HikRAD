# v4-3 gate result — Licensing v2 & security hardening

**Status: GREEN on everything this session's environment could execute;
five items have a database/live-OS leg that could not run here.** This
session's sandbox is Windows with no Postgres/Redis, no `sudo`/systemd, and
no FreeRADIUS binary — the same class of environment constraint v4-2's gate
result hit for its hardware legs. Everything NOT gated on that missing
infrastructure was not just written but actually **executed and observed
passing**, including three separate "prove the gate fails first" rehearsals
against real tooling (gitleaks, the release-manifest linter, and the
FreeRADIUS cert generator) — not simulated, not guessed. What follows is a
precise accounting; nothing below is marked green without the command that
proves it.

## What shipped (FR-122–127)

- **FR-122 — Licence v2 payload.** `Payload` gains `version`/
  `entitlements[]`/`expires_at`/`support_until`/`serial`, all `omitempty`.
  `EffectiveVersion()`/`HasEntitlement(name)` are the one place that decide
  v1-vs-v2 and what's granted; `license.KnownEntitlements` is the data
  catalogue (`white_label`, `self_service`, `api_access`, `gateways` —
  only `white_label` is wired to an enforcement point this phase, the
  other three are reserved names for future phases). v1 blobs verify
  unchanged and fall back to `DefaultEntitlements(tier)` (grants the three
  reserved names, withholds `white_label`).
- **FR-123 — File-exchange activation.** `license.ActivationRequest` +
  `POST /api/v1/license/request-blob` (server's own live fingerprint,
  hashed components, checksum). `scripts/license-tool activate -request
  <file>` verifies the checksum and signs against exactly that
  fingerprint — no `-fingerprint` flag exists on `activate` at all.
- **FR-124 — Single verified enforcement path.** `platform.LicenseSnapshot`
  replaces two separate cached atomics; `RefreshLicenseCache` re-verifies
  the stored payload's signature before adopting it (closes a real gap —
  the periodic refresh used to trust the stored payload unconditionally).
  `Evaluate` gains calendar expiry. Migration **0596**
  (`license_state_audit`, append-only, BEFORE-trigger-immutable, one row
  per actual transition).
- **FR-125 — Licence UX.** Entitlement chips, expiry, support window,
  serial on the License page; export-request/import-licence promoted to
  first-class buttons, manual entry demoted to a disclosure.
- **FR-126 — Closed-source distribution.** `scripts/lint-release-manifest.sh`
  + a new `release-manifest` CI job; `vite.config.ts` (panel, portal) set
  `build.sourcemap: false` explicitly; vendor-tooling isolation asserted
  and documented.
- **FR-127 — Security hardening.** Checked-in FreeRADIUS PKI deleted,
  generated per-install; `gitleaks` wired as CI job `secret-scan` + a
  local pre-commit hook; notification-credential encryption-at-rest gap
  closed; a WhatsApp field-name mismatch bug found and fixed in the same
  pass; the multipart-through-the-real-router test gap closed.

Thirteen commits, in the order of the phase brief's §6 plan (commit
messages carry the full rationale for each).

## Three real bugs found and fixed live, not by code review

1. **`RefreshLicenseCache` never re-verified a loaded licence's signature**
   (the actual FR-124 gap, not a hypothetical) — found by reading
   `LoadLicenseRecord`/`RefreshLicenseCache` against the phase's own "not
   forgeable" requirement, confirmed by writing a test that edits the
   stored payload directly via SQL and observing the old code (design
   only) would have adopted it. Fixed before any test was written against
   the fix, not after.
2. **`internal/monitorsvc/channels.go`'s `whatsAppConfig` used `token`/
   `phone_id`** while the panel actually saves (and
   `notify_test_send.go`'s own struct already correctly expected)
   `access_token`/`phone_number_id` — a WhatsApp channel configured
   through the panel and confirmed via its own "Test Send" button silently
   never delivered a real alert or subscriber notification. Found while
   wiring encryption for these exact fields; fixed in the same commit.
3. **An orphaned second private key** (`scripts/license-tool/
   vendor-key.b64`, distinct from the documented `dev-vendor-key.b64`,
   verified inert — its public half matches nothing embedded) was checked
   into git, almost certainly from someone running the README's own
   example `keygen` command inside the checkout instead of on an air-gapped
   machine as instructed. Found live during the `gitleaks` rollout, before
   it was even wired into CI. Deleted; gitignored so the README's own
   example command can't recreate it.

Also found, real but scoped as a documented residual risk rather than
fixed this phase: the PKCS#12 export password in `passwords.mk` stays
FreeRADIUS's stock default even though the RSA key material itself is
unique per install — see `docs/ops/security-checklist.md`.

## Security review (gate item 14)

**Auth.** No changes to `internal/auth` this phase. The one new
authenticated surface (`POST /api/v1/license/request-blob`'s extended
response) is gated by the pre-existing `license.manage` permission,
unchanged. The activation-request file itself carries no secret — it's
this server's own fingerprint, already shown unauthenticated at
`/api/v1/setup/license` for the pre-admin case.

**Uploads.** The multipart gap this phase closes (`enforceJSON`'s
real-router coverage) is a correctness fix, not a new upload surface — no
new file-accepting endpoint was added. The logo-upload path
(`branding_logo.go`) is unchanged.

**Licence path.** This is where the phase's real work concentrated. The
threat model: (a) a forged/tampered licence blob — closed by `Verify`
(unchanged, pre-existing) plus the new re-verify-on-every-load in
`RefreshLicenseCache` (this phase's actual fix); (b) a stale/replayed
activation request — the checksum catches corruption/tampering of the
request file itself, but is explicitly NOT an authentication mechanism (the
server has no private key to sign with) — the real trust boundary is
unchanged from before: the vendor's signature over the licence blob is
the only thing that ever grants anything, and the activation request is
only ever an input to a human decision at the vendor's end, never
auto-trusted by the server; (c) cap/entitlement forgery via direct DB
access — closed structurally (signature re-verify), proven by test design
even though the test itself didn't run live this session.

**Updater.** `hikrad-updaterd`/`scripts/hikrad` untouched this phase. No
new code path was added to the update pipeline.

## How to close the remaining legs

Everything in "written and designed correctly, but NOT run live" needs
exactly what v4-2's still-open items needed: a real Linux box with root, a
reachable Postgres+Redis (`HIKRAD_TEST_DB_URL`/`HIKRAD_TEST_REDIS_URL`),
and FreeRADIUS installed. On such a box:

```sh
# DB-gated Go suites (gate items 1, 3, 7, 8's DB proof, 13's DB proof)
export HIKRAD_TEST_DB_URL=postgres://hikrad:hikrad@localhost:5432/hikrad_test?sslmode=disable
export HIKRAD_TEST_REDIS_URL=redis://localhost:6379/0
cd backend && go test ./...

# Full install + cert generation + FreeRADIUS validation (gate item 11's installer leg)
sudo ./scripts/install.sh
sudo ./scripts/install.sh   # re-run — confirms certs are restored, not regenerated
diff <(sha256sum /etc/hikrad/freeradius/certs/server.key) <(...)  # compare across two separate hosts for true uniqueness

# Packet-level grace proof (gate item 8's live leg)
make -C backend test-harness-smoke
```
