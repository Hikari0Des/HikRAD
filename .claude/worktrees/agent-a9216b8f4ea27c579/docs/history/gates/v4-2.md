# v4-2 gate result — Native install, Docker removal, RouterOS target

**Status: INCOMPLETE.** Substantially more was proven live in this phase
than a typical gate result of this kind — including a full real native
install, a real packet-level RADIUS pass, a reboot-survival test, an
uninstall/reinstall cycle, and live testing against a real MikroTik router
— but three gate items still need things this session genuinely could not

stop. What follows is a precise accounting of what shipped, what was

## Nine real bugs found and fixed via live testing

Everything below was found by actually running the installer as root
against a real, freshly-provisioned Debian 13 systemd environment (WSL2
Debian, `sudo` available for this pass), not by code review — each is
also logged in `docs/ops/known-issues.md`, "Closed — v4-2":

1. **APT keyring permissions** — `gpg --dearmor`'s default `0600` output
   blocked Debian trixie's sandboxed `_apt` user from verifying the PGDG/
   TimescaleDB repos. Fixed: `chmod 0644` after both dearmor calls.
2. **TimescaleDB preload** — `CREATE EXTENSION timescaledb` failed with
   "not in shared_preload_libraries". Fixed: `timescaledb-tune` + restart
   + `pg_isready` wait before extension creation.
3. **Directory ownership via ambient umask** — `install -d -m` doesn't
   apply its mode to ancestor directories it creates implicitly, so
   `/opt/hikrad` and others inherited whatever umask the caller happened
   to have. Fixed: explicit `umask 022` + explicit ancestor `install -d`.
   This is the anti-pattern A11 bug class directly, caught live.
4. **Internal port collision risk** — the suggested default public HTTP
   port (8080) was the same number as `hikrad-api`'s internal-only
   loopback port. Fixed: named constant + validation on all three
   port-resolution paths, default suggestion moved to 8880.
5. **Hardcoded `/etc/raddb` path** in all three `rlm_exec` module configs
   — silently pointed at a path that doesn't exist under v4-2's
   `/etc/hikrad/freeradius` tree, so `authorize.pl` never ran and every
   Access-Request was rejected. Fixed: `${confdir}/scripts/....pl`.
6. **`rlm_exec` attribute-naming + environment isolation** — the hardest
   bug of the phase. FreeRADIUS 3.2.7's `rlm_exec` exposes `input_pairs`
   under the attribute's literal hyphenated name (`User-Name`), not the
   uppercase-underscore form the scripts assumed, **and** builds a fresh
   child environment that does not inherit `radiusd`'s own environment —
   so the `Environment=` lines added to the systemd unit were silently
   ineffective too. Fixed: an `envattr()` helper trying both forms in all
   three Perl scripts; systemd `Environment=` lines removed in favor of
   hardcoded loopback URL defaults.
7. **`hikrad-api.service` `226/NAMESPACE`** — missing its own
   `RuntimeDirectory=hikrad` declaration under `ProtectSystem=strict`.
   Fixed by adding it (ref-counted safely alongside other units).
8. **`hikrad uninstall --purge` orphaned the Postgres role/DB** — deleted
   `hikrad.env` (the only record of which role/DB to drop) before
   dropping them. Fixed: capture DB identity before file deletion.
9. **`scripts/hikrad` `all_units()`** used the wrong systemctl check
   (`list-unit-files` instead of `is-enabled --quiet`) with a `set -e`-
   unsafe bare `&&`. Fixed: explicit `if` blocks on the correct check.

Plus the previously-known **FreeRADIUS unquoted-`shortname` bug**
(already in `known-issues.md`, re-surfaced and confirmed live by this
exact install, since this was the first time `freeradius -CX` was ever
run for real against this code path).

## Live testing against a real router (authorized, scoped to `vlan2981-hotspot`)

With the owner's explicit authorization and real credentials, this
session tested against a live, production-adjacent MikroTik
CCR1072-1G-8S+ (hostname "Warith_University"), under a hard, explicitly
stated scope restriction: **only `vlan2981-hotspot` / the `hsprof-test`
hotspot profile may be touched — nothing else on the router.** Every
change made was additive and reversible, per the router-ownership
principle this codebase already enforces for its own NAS config pushes.

**Setup:**
- Enabled WSL2 mirrored networking (`.wslconfig`) so the WSL host became
  reachable from the router's network at its real LAN IP, confirmed via
  the router's own OSPF routing table.
- Confirmed bidirectional reachability (SSH/API from WSL to the router;
  TCP from the router's network back to WSL).
- Router changes, both scoped to the test hotspot only, both tagged
  `comment=hikrad-v4-2-test` for easy identification:
  - Added one new `/radius` client entry pointing at the WSL host's IP,
    ports 1812/1813, secret `hikradsecret123`.
  - Set `use-radius=yes` on **only** the `hsprof-test` hotspot profile.
  - Read-only verification (`/radius print detail`, `/ip hotspot profile
    print detail`) confirmed no other config was touched.
- Registered the router as a new NAS in HikRAD at its real egress IP,
  deliberately never previously seen by this HikRAD instance, with no
  FreeRADIUS restart issued afterward — set up specifically to exercise
  the dynamic-clients zero-restart path (gate item 9) rather than the
  static regenerate-and-reload path.

**What this proved:**
- Real bidirectional network reachability between HikRAD and a real
  MikroTik across a routed network.
- The additive/scoped router-config-push pattern works against a real
  device without disturbing anything outside the authorized scope.
- NAS registration with zero explicit `systemctl restart` of the RADIUS
  worker.

**What this did not reach:**
- A real captive-portal hotspot login. `curl` against the hotspot
  gateway's `/login` returned `404` on GET and `501 Not Implemented` on
  POST. Root cause (not further chased given time available): RouterOS's
  hotspot captive-portal interception applies only to traffic it
  recognizes as coming from an unauthenticated client **directly attached
  to the hotspot's own L2 segment** — a routed request arriving from
  outside that segment (as everything from this WSL vantage point
  necessarily is) isn't intercepted the same way a real client's browser
  request would be. Reaching a genuine end-to-end login would need a
  device (physical or virtual) actually joined to `vlan2981-hotspot`,
  which wasn't available.
- As a direct consequence, **no real RADIUS Access-Request from the
  router was ever confirmed to arrive** at `hikrad-radius-worker`. The
  dynamic-clients mechanism was set up correctly (real NAS row, no
  restart since registration) but was never exercised by an actual packet
  from real router traffic — gate item 9 remains genuinely open, not
  "probably fine."
- The RouterOS **container image** (`deploy/routeros/`) was never built
  or imported onto this device. That would be a materially different,
  invasive change (installing HikRAD's own workload onto the router
  itself) that the owner's authorization did not extend to — the
  authorization was for testing RADIUS/hotspot integration against the
  test hotspot, not for deploying software onto a production university
  router. Gate items 13/14 are correctly still untouched, not an
  oversight.

**Router state left behind:** the two additive, `hikrad-v4-2-test`-tagged
changes (the RADIUS client entry and `hsprof-test`'s `use-radius=yes`)
were left in place, since they're harmless, clearly labeled, scoped to
the authorized test hotspot, and may be useful for a follow-up session
that has access to a device on that VLAN. They are trivially reversible
(`/radius remove [find comment=hikrad-v4-2-test]`; `/ip hotspot profile
set hsprof-test use-radius=no`) if the owner would rather they weren't
there.

## How to run this yourself

For continued exercising of the still-open items (2, 4, 12, 13/14, and a
real end-to-end hotspot login for item 9), you need either a device
physically/virtually attached to `vlan2981-hotspot` (for a genuine
captive-portal login), a second real MikroTik for a PPPoE timing run, or
a restorable Compose-era backup for the migration rehearsal.

For day-to-day development (not exercising the installer itself), the
lighter loop is `make dev-env && make dev-up` — see
[docs/ops/dev-setup.md](../../ops/dev-setup.md), including how to reset
your local database (`make dev-down`) or start over completely.

For exercising the installer itself against a real, disposable systemd
Linux environment (what this session used):

```sh
wsl -d Debian
cd ~ && git clone <this repo, or copy it in>   # into the distro's own filesystem, not /mnt/c
cd hikrad
sudo ./scripts/install.sh                       # fresh install
sudo ./scripts/install.sh                       # run it again — confirms idempotency yourself
sudo ./scripts/hikrad doctor                     # health check
sudo ./scripts/hikrad uninstall --purge          # full teardown, including the DB
```
