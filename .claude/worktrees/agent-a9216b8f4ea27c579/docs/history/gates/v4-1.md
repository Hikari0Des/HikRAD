### 7. No flash — **PARTIAL (mechanism verified, pixel observation needs item 9's browser)**

Two independent mechanisms, per the brief:

1. **Explicit stored `light`/`dark`** — a synchronous inline script, first thing in both `index.html`'s `<head>`, reads `localStorage['hikrad.theme']` and stamps `data-theme` before anything else loads. Verified in the actual `vite build` output that this script is emitted **before** the injected `<link rel="stylesheet">`:
   ```
   <script>...localStorage.getItem('hikrad.theme')...</script>
   ...
   <script type="module" crossorigin src="/assets/index-*.js"></script>
   <link rel="stylesheet" crossorigin href="/assets/index-*.css">
   ```
   (full script runs and returns before the parser reaches the stylesheet link, which is what removes the flash — order confirmed in `dist/index.html` for both apps.)
2. **`system` preference** — `tokens.css`'s new `@media (prefers-color-scheme: dark)` block, guarded with `:not([data-theme='light'])`, resolves from the OS alone with zero JS. Its values are asserted byte-identical to `:root[data-theme='dark']` by `contrast.test.ts`'s parity test (`expect(fallback).toEqual(dark)`), so it can't silently drift out of sync with the "real" dark theme.

What's verified: the mechanism is structurally correct (script ordering in real build output, values provably identical, both code paths exercised by tests). What's **not** verified: actually setting the OS to dark, clearing storage, and watching a real screen paint dark on the very first frame — that requires a browser, which is item 9's blocker.
