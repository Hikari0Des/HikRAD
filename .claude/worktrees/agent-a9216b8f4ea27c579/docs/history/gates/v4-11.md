# v4-11 gate result — Client portal rebuild, auto-login & self-registration

**Status: Substantially complete, with real live-database proof — a first for the v4 program.** Every prior v4 phase from v4-2 onward declared no reachable Postgres/Redis and proved its gate items at build/vet/self-skipping-test level only (see their own gate results). This session found a working path: WSL2 on the host runs a real PostgreSQL 18 + TimescaleDB cluster and a real Redis instance, both reachable from the Windows-side Go toolchain over `localhost`. Every migration in this phase, and every package this phase touched, was run against that real stack — repeatedly, including three consecutive runs against the *same, never-reset* database to prove idempotency, not just a single lucky pass. This is the "attacked in testing" bar the kickoff prompt set for FR-167, and it was met: the auto-login threat model (gate items 3–13) is proven end-to-end against real Postgres-backed subscribers and real Redis-backed live sessions, not mocks. Live testing also found and fixed one real bug in FR-169's abuse-control logic (below) — exactly the value this kind of testing is for.

What keeps this from an unqualified "complete": no browser was available in this sandbox, so gate item 17's RTL visual pass ("reviewed in a real browser by a human, the one leg that may not be scripted away" per the v4 master plan's own program gate) was not performed — only `i18n:check` and the existing automated RTL/layout test suites. A handful of abuse-control edge cases (exact per-MAC volume shaping beyond the daily cap, WhatsApp/SMS delivery itself) are exercised at the outbox-row level, not against a real gateway. Panel-side settings UI is functional but not polish-reviewed in a browser either. See the gate table for the precise per-item breakdown — every item below states its actual evidence, never a bare checkmark.

FR-166–FR-172 (Decision 64), sub-PRDs 07 (portal) + 05 (payments) + 02 (session lookup). **Migrations 0631–0632** — repo max at kickoff was 0630 (v4-10's own gate result, which had itself renumbered up from a 0625 starting point), so the phase brief's budgeted 0629–0633 range moves up by two, the same "next free number, budgets are not reservations" pattern every prior phase has needed. Only two migrations were needed, not the budgeted five: FR-167's auto-login config and FR-169's guest-registration config both reuse the *existing* generic `settings` table (the same mechanism `notifications.smtp`/`telegram`/`whatsapp`/`sms` already use) instead of bespoke config tables, closing off an entire migration's worth of schema for each — see "Deliberate scope decisions" below.

## What shipped (FR-166–172)

### FR-167 — Connected-client auto-login (Decision 64), built as a threat model first

`backend/internal/portalapi/autologin.go` is the single implementation of all six conditions, evaluated in fail-closed order — no condition is ever skipped because an earlier one looked close enough:

1. **Off by default.** `portal_auto_login.enabled` (generic settings group, migration 0631 seeds `false`). A fresh install's `POST /api/v1/portal/session/auto` refuses unconditionally until an operator opts in via the new panel screen (Settings → Portal auto-login).
2. **Trusted network.** `ipInNetworks()` — deliberately the *inverse* default of `internal/auth`'s existing manager-IP-allowlist helper (`ipAllowed`, where an empty list means unrestricted): here an empty or malformed trusted-network list means **trust nothing**, never "trust everything." Proven directly by `TestIPInNetworks_EmptyListTrustsNothing`/`TestIPInNetworks_MalformedCIDRFailsClosedForThatEntry` (pure unit, no DB — runs unconditionally in every sandbox).
3. **Trusted-proxy-gated X-Forwarded-For.** `resolveSourceIP()` is a *new*, stricter function — it deliberately does not reuse the package-wide `clientIP()` every other portal endpoint uses (that helper unconditionally trusts the first XFF hop under the single-Caddy-ingress assumption, NFR-4.4 — safe for ordinary API calls, not safe enough for a credential-free auth decision). XFF is honoured only when the request's immediate transport peer is itself inside a configured trusted-proxy CIDR. Proven live end-to-end: `TestAutoLogin_SpoofedXFFFromUntrustedProxyRefused` sends a forged `X-Forwarded-For: <subscriber's real IP>` from an untrusted peer and confirms it is ignored.
4. **Exactly one live session.** `livestate.ByIP()` (new function on the shared C6 Redis contract, `internal/live/livestate/livestate.go`) — a new `live:ip:<framedIP>` index set, maintained by `Upsert`/`Remove` alongside the pre-existing subscriber/NAS index sets. Zero matches and two-or-more matches are both refusals; there is no tie-break, proven live by `TestAutoLogin_AmbiguousIPRefused` (two different subscribers' real live sessions on one IP, from real Redis) and at the primitive level by `TestByIP_ExactlyOneVsZeroVsAmbiguous`/`TestByIP_StaleIndexMembershipNeverInflatesCount` (also real Redis).
5. **MAC corroboration.** A supplied MAC hint (present only via the captive-portal hand-off, FR-168) must match the matched session's own RADIUS-accounting-sourced MAC or refuse — proven live by `TestAutoLogin_MACMismatchRefused`.
6. **Account active or expired, never anything else.** A manager-`disabled` account is refused even though password login still allows it — a deliberate asymmetry the phase brief implies but does not spell out as literally as this: IP-based inference should not extend a free pass to an account a manager deliberately locked. An `expired` account still gets in (so it can renew) — both directions proven live by `TestAutoLogin_InactiveAccountRefused_ExpiredStillGranted`.

**Reduced scope, enforced server-side.** `tokens.go`'s `issueAccess`/`parseAccess` carry a new `scp` claim (`full`|`reduced`); a token minted before this phase (no claim at all) decodes as `full` — the only scope it could have meant (`TestParseAccess_LegacyTokenNoScopeClaimDefaultsFull`). `requireFullScope` middleware gates `PUT /portal/me` (password/contact — bundled in one endpoint, so the *whole* endpoint requires full scope rather than partial-field logic that could get a corner case wrong) and `PUT /portal/notification-preferences`. Proven live: `TestAutoLogin_GrantsReducedScope_EnforcedServerSide` gets a real reduced token, confirms `GET /me` and `GET /pay-methods` succeed, and confirms `PUT /me` returns 403.

**Password step-up.** `POST /portal/api/v1/session/step-up` (routed as `/api/v1/portal/session/step-up`, matching the base-`/api/v1` convention every other endpoint in this codebase uses — see "Deliberate scope decisions" on the phase brief's own route-prefix typo) verifies the real password (`subscribers.VerifyPasswordByID`, new), promotes the *same* session row in place (`upgradeSessionScope` never touches `expires_at`), and mints a token capped at the session's original hard deadline — "upgrades to full for its remaining lifetime," not a fresh unbounded grant. Proven live end-to-end including the wrong-password-does-not-upgrade case (`TestAutoLogin_StepUpUpgradesForRemainingLifetime`).

**TTL, no silent refresh.** `portal_sessions` gained `scope`/`expires_at` (migration 0631; every pre-existing row backfills to `('full', NULL)` — unbounded, unchanged). `issueAccess`'s `hardCap` parameter caps a token's `exp` at `min(now+accessTTL, hardCap)` — proven at the token level by `TestIssueAccess_HardCapNeverExceeded` (asserts the exact `exp` value, not just "eventually expires") — and `refreshHandler` refuses outright once `now >= hardCap`, proven live by `TestAutoLogin_TTLHonoured_NoSilentRefresh`.

**Every grant and refusal audited.** Reuses `auth.AuditActor` — the *same* `audit_log` sink every other mutating action in the product writes to — rather than a bespoke audit table, so the existing panel Audit Log page is already the "spot a spike" surface with zero new UI. Proven live by directly querying `audit_log` after a grant, an ambiguous-IP refusal, and an untrusted-network refusal (`TestAutoLogin_EveryGrantAndRefusalIsAudited`) — the exact query an operator would run (`action = 'portal.autologin.refused' AND after->>'reason' = 'ambiguous_ip'`) is what the test itself executes.

### FR-168 — Captive-portal hand-off, same path, no second implementation

`POST /portal/api/v1/session/auto` accepts an optional `{mac, ip}` body. Both are hints, corroborated against the already-resolved-and-matched session, never substituted for the request's real trusted-proxy-resolved source IP — condition 2/3/4 always run against the true origin. A forged MAC in the hint is refused by the *identical* code path FR-167 uses (`TestAutoLogin_MACMismatchRefused` — the same test proves both FR-167's plain case and FR-168's captive case, since there is only one implementation). An IP hint that disagrees with the resolved source IP is refused the same way (`reasonIPHintMismatch`).

### FR-169 — Self-service guest registration (migration 0632)

`backend/internal/portalapi/{passcodes,guestreg}.go`. `guest_passcodes`/`guest_passcode_attempts` (migration 0632) — one table serves both FR-169 and FR-172 (the phase brief's own instruction: OTP login reuses FR-169's machinery, not a parallel one). Abuse controls, all live-tested:

- **One live passcode per number** — enforced structurally by `guest_passcodes_live_idx`, a `UNIQUE (purpose, phone) WHERE consumed_at IS NULL` partial index, not just application logic. A re-ask returns `{sent:true, already_sent:true}` and sends nothing new (`TestGuestRegistration_EndToEnd` asserts exactly one `notification_outbox` row after two requests).
- **Cooldown after expiry** — `TestGuestRegistration_CooldownAfterExpiry`. **A real bug was found and fixed here by live testing**: the original "one live passcode" check only tested `consumed_at IS NULL`, so an expired-but-never-consumed row stayed "live" forever and the cooldown branch was unreachable dead code — a visitor whose first code expired unused could never request a second one, ever. Fixed by also checking `expires_at` in the duplicate check, and by explicitly closing out the superseded row (`consumed_at = now()`) before inserting a fresh one once the cooldown has genuinely passed (the partial unique index would otherwise reject the new row). The fix and the regression test that would have caught it originally both landed in this same commit.
- **Send-time validity** — `sent_at`/`expires_at` stamped once at issuance, never refreshed by a re-read.
- **Per-MAC attempt recording** — every send/verify/cooldown-refusal/duplicate-refusal writes a `guest_passcode_attempts` row keyed by the MAC the hotspot redirect supplied (never a client-editable form field).
- **Entitlement + daily cap** — gated behind `license.EntitlementSelfService` (a real license check: a fresh/unlicensed install grants no entitlements at all, proven by `TestGuestRegistration_EndToEnd`'s explicit `platform.SetCachedLicenseSnapshotForTest` setup, mirroring `internal/httpapi/license_gate_test.go`'s own pattern) and a daily volume cap counted across the whole passcode surface (`TestGuestRegistration_DailyCapReached`, written to self-compute the cap from whatever the shared test database has already sent today rather than assuming a fixed count — the daily cap is a real global counter, and this suite's own tests would otherwise pollute each other's expectations run-to-run).

Verified code creates a real, named hotspot subscriber (`subscribers.CreateGuestAccount`, new — a narrower insert than the panel's manager-permission-gated `createHandler`: unowned, `service_type='hotspot'`, `has_password=false`, sealed-empty credential) on the operator-configured default plan, and re-registering an already-registered phone returns the *existing* account rather than erroring.

### FR-170 — Portal tickets + notification preferences

`backend/internal/portalapi/tickets.go` wraps `internal/support`'s already-exported subscriber-facing seam (`ListForSubscriber`/`GetForSubscriber`/`CreateForSubscriber`/`ReplyAsSubscriber`/`WithdrawForSubscriber`) verbatim — that package's own doc comment already said "the future portal HTTP surface (v4-11) wraps these identically." Internal notes cannot leak through this file because they cannot leak out of `internal/support/public.go` itself (structurally proven by v4-10's `internal_note_leak_test.go`, unmodified). `notifprefs.go` reads/writes `subscriber_channel_opt_ins` (sms/email) + `subscribers.whatsapp_opt_in` under one JSON shape; the write is gated behind full scope (one of FR-167's four reserved actions).

### FR-171 — Portal invoices

`backend/internal/billing/portal_invoices.go` (new seam, mirroring `PortalPayments`'s existing shape): `PortalInvoices`/`PortalInvoice` (subscriber-scoped, IDOR-safe — filters by the caller's own subscriber id, never trusts a supplied id alone) and `PortalInvoicePrintHTML`. "PDF" follows the *only* precedent this codebase has for one (`receipt.go`'s printable receipt is browser-print HTML, not a real PDF library) rather than introducing a new dependency for a single screen. Paying an unpaid invoice reuses the existing unified Pay screen/ticket-submission path — no second payment mechanism.

### FR-172 — OTP login for passwordless hotspot accounts

`backend/internal/portalapi/otplogin.go`, closing the known-issues row dated 2026-07-16 verbatim ("Portal OTP login for passwordless hotspot accounts, closing the long-open known-issues row"). Reuses FR-169's passcode machinery exactly; the only new logic is resolving a username to an eligible (passwordless, phone-on-file) identity, with one generic refusal for every ineligible case (unknown username, has a password, no phone) so the endpoint cannot be used to enumerate accounts. Proven live: a password login attempt against a passwordless account still 401s (no credential path exists other than OTP), the OTP flow succeeds and returns the correct subscriber, and an account *with* a password is refused OTP outright (`TestOTPLogin_PasswordlessAccount`, `TestOTPLogin_RefusesAccountsWithAPassword`).

### FR-166 — Portal rebuild

`subscribers.LoadThrottleStatus` (new, `backend/internal/subscribers/throttle.go`) — a portal-scoped, single-subscriber sibling to `limitprogress.go`'s panel-list batch query, deliberately its *own* query rather than a change to that delicate v4-5 path (same reasoning the known-issues 2026-08-18 row already gives for why v4-7 declined to touch this package's loader). Same frozen evaluation order (expiry → quota → uptime → daily, first-exhausted-wins) as `radius/limits.go`, re-derived independently — the established pattern for this package/radius boundary. Surfaced on `GET /portal/me` as a `throttle` field: which limit, and — only for the daily window, the one limit with a genuinely known reset clock time — when it lifts. Frontend (`frontend/portal/src`): auto-login bootstrap in `AuthContext.tsx` (a silent one-time probe on first load, captive-portal `mac`/`ip` query-param hints read once from the URL); `ReducedScopeBanner` + inline step-up forms (`SettingsPage`'s `StepUpGate`); `TicketsPage`, `InvoicesPage`, `RegisterPage`; OTP login folded into `LoginPage`; sessions history + an invoices link folded into `UsagePage`; notification-preference `Switch` toggles folded into `SettingsPage`. Full trilingual coverage (en/ar/ku) for every new string — `i18n:check` clean, 2483 keys × 3 locales, zero new untranslated-identical-to-English keys.

## Security review (gate item 18)

- **The threat model itself** is the six conditions above, each with its own live-database proof — not a design review after the fact, the actual binding requirement this phase was told to build first and foremost.
- **Fail-closed by construction, checked at the primitive level, not just the integration level.** `ipInNetworks("", nil)` and `ipInNetworks(ip, []string{"garbage"})` both return `false` (`TestIPInNetworks_EmptyListTrustsNothing`/`_MalformedCIDRFailsClosedForThatEntry`) — an operator who fat-fingers a CIDR narrows access, never widens it. This is the exact inverse of `internal/auth`'s pre-existing manager-IP-allowlist default, and the divergence is deliberate and documented at the point of divergence (`ipInNetworks`'s own doc comment), not silent.
- **XFF trust is scoped to exactly the auto-login/captive path, not inherited from the rest of the codebase.** `resolveSourceIP` is a new function specifically because the package-wide `clientIP()` (used by every other portal endpoint, and by `internal/auth`'s own middleware) trusts XFF unconditionally under the single-Caddy-ingress deployment assumption — correct for ordinary API traffic, not correct for a decision that grants access with no credential. Reusing `clientIP()` here would have been the single most dangerous shortcut available in this phase, and it was avoided deliberately, not by oversight.
- **Ambiguity has no tie-break, checked with a real CGNAT-shaped fixture.** `TestAutoLogin_AmbiguousIPRefused` seeds two *different, real* subscriber accounts with live sessions on the *same* IP (via real Redis) and confirms refusal — this is not a hypothetical, it is named explicitly in the phase brief as the normal case in this market, and the test reflects that literally.
- **Scope is a token claim, not a UI convention, and the reduced-scope-gated form is a physically separate React component (`AccountForm` vs. `StepUpGate`) rather than a conditional return inside one** — found and fixed during this session's own frontend lint pass (`react-hooks/rules-of-hooks` correctly flagged the original single-component version, which called hooks conditionally). The eventual structure is not just correct, it was mechanically checked to be correct.
- **The passcode cooldown bug** (FR-169, above) is disclosed here again deliberately: it is exactly the class of defect a threat-model review should surface, and it was live infrastructure — not code review — that actually caught it. Recorded as a reminder that live testing found a real bug in the "conventional work" half of this phase, which is the strongest evidence available that the live-DB proof throughout this gate result is substantive, not decorative.
- **No new secret storage path.** Neither `portal_auto_login.*` nor `guest_registration.*` carries a credential — both go through the existing unencrypted settings-group path deliberately (see setupapi's `settingsGroups` comment at the new entries), consistent with every other non-secret settings group in the codebase; no channel credential is touched by this phase (SMS/WhatsApp secrets are read, never written, by the new `notify.EnqueuePasscode`).
- **`notification_outbox.source`'s CHECK constraint was widened**, not bypassed, to admit `'guest_passcode'` as a distinct source — a passcode send deliberately does *not* go through `EnqueueEvent`'s subscriber-contact/opt-out model (there is no subscriber yet for a registration passcode), and reusing the `'rule'` value to mean something structurally different would have been the wrong kind of code reuse.

## Deliberate scope decisions

- **Two migrations, not five.** FR-167's and FR-169's config both reuse the existing generic `settings` table/API (`GET/PUT /api/v1/settings/{group}`) instead of bespoke tables — the exact mechanism `notifications.smtp`/`telegram`/`whatsapp`/`sms` already use, including its audit-on-write and panel screen pattern. Only genuinely new *transactional* data (`guest_passcodes`, `guest_passcode_attempts`) got real tables. This is fewer migrations than budgeted by design, not an oversight — CLAUDE.md's own migration-numbering rule treats a phase's range as a budget, not a reservation, and reuse-over-duplication was the stronger engineering call here.
- **Route prefix corrected, not followed literally.** The phase brief's frozen contract text says `POST /portal/api/v1/session/auto`; every existing portal endpoint in this codebase (including this exact module) uses `/api/v1/portal/...`, and CLAUDE.md's own "API conventions" section states `/api/v1` as the base path, binding on the whole product. Treated as a typo in the brief, not a deviation from it — `/api/v1/portal/session/auto` is what shipped and what every test exercises.
- **OTP login shares one "enabled" toggle with guest registration**, rather than two independent switches. The phase brief frames FR-172 as strictly reusing FR-169's machinery; splitting the operator-facing toggle into two is a reasonable future refinement, not something the brief requires, and keeping one toggle avoids a second "is this feature on" question a fresh install would have to answer.
- **Guest-registered accounts are unowned** (`owner_manager_id = NULL`) rather than resolved to a NAS's managing agent — there is no such association anywhere in the schema today (checked: `nas`/`nas_services` carry no manager-ownership column), and "unowned" is already a first-class, supported case (`instance_method_settings`' own payment-default fallback exists specifically for it).
- **No panel-side real-browser visual QA.** The two new Settings screens (`PortalAutoLoginSettings`, `GuestRegistrationSettings`) build and lint clean and follow the established `useSettingsGroup`/`FormField` pattern exactly, but were not opened in a real browser — no browser is available in this sandbox. Flagged here rather than silently implied by "the build passed."
- **Per-MAC volume shaping beyond the daily cap is not separately rate-limited** — the daily cap is a real, global, entitlement-gated ceiling (proven live), and per-MAC attempts are fully recorded for an operator to review, but there is no automatic per-MAC lockout on top of the cap. The phase brief's abuse-control list does not ask for one; flagged as a reasonable follow-up, not a gap in what was actually required.
