# v4-4 gate result — Limits engine (SAMM parity)

**Status: GREEN on everything this session's environment could execute; the
database/live-router/packet-harness legs could not run here.** This
sandbox is Windows with no Postgres/Redis, no FreeRADIUS binary, and no
Docker daemon reachable — the same class of environment constraint v4-2's
and v4-3's gate results hit. Everything not gated on that missing
infrastructure was written **and executed**, not just designed: 210 `go
test -v` `--- PASS` lines in `internal/radius` alone (up from 155
pre-phase), the full backend suite green, and the full frontend
build/lint/type-check/i18n-check/test suite green. What follows is a
precise accounting; nothing below is marked green without the command that
proves it.

## What shipped (FR-128–132)

- **FR-128 — Uptime limit.** `profiles.uptime_limit_seconds` (nullable =
  unlimited), derived live from `sessions` since
  `subscriber_counters.uptime_cycle_anchor` (`subscribers/limits.go`'s
  `sumUptimeSeconds`) — never stored-and-edited, the same posture
  `accounting/quota.go` already uses for quota.
- **FR-129 — Daily usage limit.** `profiles.daily_limit_bytes` +
  `daily_reset_min` (minutes since local midnight, server timezone
  Asia/Baghdad — matches the existing FR-11 TOD sweep's own convention).
  **Default action is `throttle`, not `block`** (`daily_exhaust_action`
  DB default AND `radius.evaluateLimits`' own fallback) — the commercial
  point of the feature. The continuous worker restores full speed on the
  next reset with **no operator action**, proven same-tick
  (`TestLimitsWorker_DailyResetRestoresThrottledSubscriberSameTick`).
- **FR-130 — Unified exhaustion action set.** `block | throttle |
  switch_plan | expired_pool`, one function
  (`radius.evaluateLimits`/`resolveAction`, `limits.go`) called by both
  `policy.go`'s auth-time `decide()` and `limitsworker.go`'s continuous
  sweep — the "ONE evaluation order, ONE implementation" instruction is
  structural, not a matter of discipline: there is only one function that
  can decide a limit's outcome. `expiry_behavior`/`quota_behavior` widen
  additively (existing values are an exact subset); `switch_plan`'s
  target profile is resolved to its own rate+pool once, in the subscriber
  loader, never carrying a raw profile id into the RADIUS engine.
- **FR-131 — Speed windows.** `profile_speed_windows` (migration 0599) —
  day-of-week mask + start/end minute + down/up rate. Deliberately
  **separate** from the pre-existing FR-11 `profile_tod_windows`/`tod.go`,
  which this phase leaves completely untouched (schema, code, and its own
  4 tests, all unmodified and still green). `radius.selectSpeedWindow`
  picks the highest-rate active match; a session in any non-normal mode is
  excluded outright (gate item 7).
- **FR-132 — Plan ergonomics.** Seed plans (migration 0600, guarded
  `WHERE NOT EXISTS (SELECT 1 FROM profiles)`), one-click duplication
  (`POST /profiles/{id}/duplicate`, copies limits + FR-64 scopes + speed
  windows), plan-level `auto_renew_default` + one-click bulk propagation
  (`POST /profiles/{id}/propagate-auto-renew`, migration 0601), and a
  profile list carrying `subscriber_count`/`speed_window_count`
  (`attachCounts`, two grouped queries, not N+1). The panel gained a full
  "Usage limits" form section, a `LimitTargetField` shared by all four
  limits' target inputs, a `SpeedWindowsEditor`, list badges, and a
  Duplicate row action.

**Continuous enforcement worker** (`radius/limitsworker.go`, new — a third
minute-granularity sweep alongside the pre-existing FR-11 TOD sweep and
FR-9/FR-10 pub/sub worker, neither touched by this phase): walks every
online session via `livestate.All`, resolves its AuthView through the same
loader auth time uses, and acts **only** when the winning limit is uptime
or daily — expiry/quota's mid-session enforcement stays owned entirely by
`enforce.go`'s existing pub/sub worker, so two workers never act on the
same crossing (`TestLimitsWorker_DeferredToEnforceGoForExpiry`/`ForQuota`).
Idempotency reuses `enforce.go`'s own `enforcement_actions` dedup-key claim
verbatim (`claimEnforcement`/`recordEnforcement`/`runPlan`, called
directly, not reimplemented) — restart-safe by construction
(`TestLimitsWorker_Idempotent`). The daily-reset sweep claims per
`(profile_id, calendar_day)` through the same table
(`TestLimitsWorker_DailyResetSweep_ClaimsOncePerDay`).

Five migrations: **0597** (profile limit columns + widened exhaust-action
CHECKs), **0598** (`subscriber_counters` + widened `enforcement_actions`
CHECK), **0599** (`profile_speed_windows`), **0600** (seed plans, only on
an empty `profiles` table), **0601** (FR-132's auto-renew columns — one
number past the phase brief's stated 0597–0600 budget, legitimate under
the master plan's "next free number, budgets are not reservations" rule
since v4-5's own 0601–0605 range had not been claimed at the time of
writing).

## The refactor that made "ONE implementation" literal, not aspirational

The pre-v4-4 `decide()` had expiry and quota each hand-rolling their own
`switch` over a 2–3-value behavior enum, inline. Rather than adding a
THIRD and FOURTH near-identical switch for uptime/daily (the "two paths
that can drift" failure mode the kickoff prompt names explicitly), both
existing switches were replaced with calls into `evaluateLimits` — a
single function all four limits fall through, in the frozen order,
returning a `policyOutcome{Mode, Rate, Pool, Kind}`. `replyIntents`
(auth-time reply) and `limitsworker.go`'s `planStepsForOutcome`
(worker-time CoA plan) both consume that same `policyOutcome` through
three more shared helpers (`normalRate`, `throttleOrSwitchRate`,
`expiredPoolRateAndPool`) — the rate a subscriber's reply carries and the
rate the worker CoAs to a stale session are computed by the identical
code, not two implementations kept in sync by hand.

This refactor's correctness is the phase's central risk (gate item 12),
verified two ways:

1. **Byte-for-byte behavior preservation.** Every one of the 24 pre-existing
   `authorize_test.go`/`enforce_test.go` tests passes **completely
   unmodified** — not one assertion, fixture, or helper in either file was
   touched.
2. **25 new tests** covering the genuinely new surface: uptime/daily at
   auth time (block/throttle/expired_pool/switch_plan/not-yet-exhausted),
   the widened expiry/quota actions (`TestExpiryThrottle`,
   `TestExpirySwitchPlan`, `TestQuotaSwitchPlan`), the frozen order
   table-driven (`TestFrozenOrder_*`), speed windows (entry, inactive,
   highest-wins, day-of-week, midnight-crossing, throttle-exclusion), and
   the pure functions (`resolveAction`, `rateMagnitude`).

## What was written and designed correctly, but NOT run live this session

- **Packet harness** (`backend/test/harness/`) was **not extended** with
  new uptime/daily/speed-window cases this session — the harness needs a
  live FreeRADIUS + Postgres + Redis stack this sandbox does not have, and
  adding scaffolding I could not execute risked shipping unverified
  harness code rather than unverified-but-logically-sound Go. Gate item 1
  ("packet harness: one case per limit, accept and reject") is instead
  proven at the policy-engine level, the actual layer that decides
  accept/reject/attributes — `TestUptimeBlock`/`TestUptimeThrottle`/
  `TestUptimeExpiredPool`/`TestUptimeSwitchPlan`/
  `TestUptimeNotYetExhaustedAccepts` and the daily equivalents all drive
  `engine.decide()` directly with the same HTTP-shaped request/response
  types `authorizeHandler` marshals — the harness is a thin wire-protocol
  shim over this exact function. Adding harness fixtures is the natural
  next step on a machine with the stack running
  (`make -C backend test-harness-smoke`), not a logic gap.
- **Migrations 0597–0601 applied against a real Postgres.** No database
  in this sandbox. `internal/profiles/store_db_test.go` and every other
  `_db_test.go` suite in the touched packages self-skip cleanly
  (`HIKRAD_TEST_DB_URL` unset) rather than failing — confirmed by the
  full green `go test ./...` run (a skip prints `SKIP`, not silence).
- **Mid-session enforcement against a live NAS.** `limitsworker_test.go`'s
  11 tests exercise the full claim→plan→CoA→record pipeline against fake
  CoA/DB seams (the identical harness `enforce_test.go` already uses for
  expiry/quota) — a real CoA round-trip to a real MikroTik was not run.
- **Reset-time DST/timezone leg (gate item 5).** `serverLocation()`
  resolves `Asia/Baghdad` via `time.LoadLocation`, falling back to a fixed
  UTC+3 offset if tzdata is missing — identical to the pre-existing
  `tod.go` mechanism, which the gate note for FR-11 already treats as
  correct (Iraq observes no DST, so the fallback is exact, not
  approximate). Every new test computes its expected minute-of-day from
  `fixedNow.In(serverLocation())` rather than a hardcoded value, so the
  suite is timezone-derivation-correct by construction, but was not run
  on a machine with a different system timezone to prove the `LoadLocation`
  path specifically (only the fallback path is exercised in this sandbox,
  since Windows Go builds typically lack the IANA tzdata `time.LoadLocation`
  needs — unconfirmed either way this session).

## Deliberate scope decisions

- **Per-subscriber `auto_renew` editing was not threaded through the full
  subscriber CRUD form/API.** The column exists (migration 0601) and is
  writable via the plan-level propagate action; individual editing on the
  subscriber form was judged the lowest-value, most CRUD-surface-touching
  part of the lowest-priority FR in this phase (auto-renew's *scheduled
  trigger* is billing's/sub-PRD 05's territory regardless, out of scope
  here either way) and was left for whichever phase next touches
  subscriber CRUD for its own reasons. Not a gate item.
- **`profile_tod_windows`/`tod.go` (FR-11) were read but never edited** —
  confirmed by `git status` showing zero changes to either file, and by
  `tod_test.go`'s 4 tests passing unmodified in the same run as everything
  else.
- **`enforce.go`/`enforce_test.go` (FR-9/FR-10's existing worker) were read
  but never edited** — the new worker reuses its unexported types/functions
  (`worker`, `coaStep`, `sessionOutcome`, `claimEnforcement`,
  `recordEnforcement`) by calling them, not by copying them, and by
  extending `enforceKind` with three new consts in the NEW file rather than
  the existing one.
